> Source files: `nym-node-status-api/nym-node-status-api/src/testruns/{mod,queue,models}.rs`, `http/api/testruns.rs`, `http/state.rs`, `http/server.rs`, `db/queries/testruns.rs`, `db/models.rs`, `nym-node-status-client/src/{lib,api,models,auth}.rs`

## Purpose

Defines gateway test-run orchestration: a background queuer that enqueues probe and ports-check test runs for bonded gateways, and the authenticated `/internal/testruns` API that assigns test runs to external agents (attaching ecash ticket materials) and ingests their signed results.

## Requirements

### Requirement: The background queuer SHALL enqueue idempotent probe test runs and re-queue stale ones

The test-run queuer MUST loop: re-queue stale in-progress test runs (those assigned before the stale window, default 7200s), then iterate all gateways ordered by last-testrun time, filter to bonded gateways, and queue a probe run per gateway, then sleep the refresh interval (default 450s). Enqueue MUST be idempotent — if a non-complete Probe run already exists for a gateway it MUST be reused rather than duplicated; otherwise a new `Queued`/`Probe` row is inserted. Unknown gateways MUST be rejected.

#### Scenario: Idempotent enqueue
- **GIVEN** a bonded gateway that already has a non-complete Probe test run
- **WHEN** the queuer processes it
- **THEN** the existing run is reused and no duplicate is inserted

#### Scenario: Stale in-progress run re-queued
- **GIVEN** an in-progress test run older than the stale window
- **WHEN** the queuer refreshes stale runs
- **THEN** it is set back to Queued so it can be reassigned

### Requirement: A scheduler SHALL periodically enqueue due ports-check test runs

A ports-check scheduler MUST run every 10 minutes and enqueue `Queued`/`PortsCheck` rows for bonded gateways whose last ports check is null or older than 14 days, deduplicating against any pending PortsCheck run. It MUST be enabled when `PORTS_CHECK_SCHEDULER_ENABLED` is unset or set to one of `1`, `true`, `TRUE`, `yes`, `YES`, and disabled for any other value (so `PORTS_CHECK_SCHEDULER_ENABLED=0` and typos both disable it). Its first tick MUST fire one period after startup, and missed ticks MUST be skipped rather than burst.

#### Scenario: Overdue ports check enqueued
- **GIVEN** a bonded gateway whose last ports check is older than 14 days and has no pending PortsCheck run
- **WHEN** the scheduler runs
- **THEN** a `Queued`/`PortsCheck` test run is inserted for it

### Requirement: Testrun assignment SHALL require agent authentication, freshness, capacity, and ticketbooks

`GET /internal/testruns` and `GET /internal/testruns/ports-check` MUST: authenticate the request (agent public key registered in the configured `agent_key_list` and a valid ed25519 signature); enforce request freshness (reject requests whose timestamp is older than the freshness window, default 120s); reject when the in-progress count is at or above `agent_max_count` (503); take the assignment mutex to serialize assignment; require enough ticketbooks of all buffered types; then atomically claim the oldest queued run (by `created_utc`) of the matching kind for a bonded gateway with performance > 0 using `FOR UPDATE ... SKIP LOCKED`; attach ticket materials; and return a `TestrunAssignmentWithTickets`.

The capacity check MUST differ between the two routes: the probe route counts **all** in-progress test runs regardless of kind, while the ports-check route counts only in-progress `PortsCheck` runs. Failure statuses MUST be: 401 for an unregistered key, a bad signature, or a stale/unparsable timestamp; 503 with the body `No testruns available` when at capacity or when nothing is queued; 500 with the body `Internal server error` when the ticketbook store cannot be checked, holds too few ticketbooks, or ticket materials cannot be assigned. A ticketbook shortage MUST NOT be reported as 503, so agents treat it as a hard error rather than an idle poll.

#### Scenario: Unregistered agent rejected
- **GIVEN** a request signed by a public key not in `agent_key_list`
- **WHEN** it requests a test run
- **THEN** the API returns 401 with the body `Make sure your public key is registered with NS API`

#### Scenario: Stale request rejected
- **GIVEN** a signed request whose timestamp is older than the freshness window
- **WHEN** it is received
- **THEN** the API returns 401 and no test run is assigned

#### Scenario: Capacity limit reached
- **GIVEN** the in-progress test-run count is at `agent_max_count`
- **WHEN** an agent requests a test run
- **THEN** the API returns 503 with the body `No testruns available` without assigning

#### Scenario: Ticketbook shortage is an internal error
- **GIVEN** fewer buffered ticketbooks than required for one of the buffered ticket types
- **WHEN** an agent requests a test run
- **THEN** the API returns 500 with the body `Internal server error` and no run is claimed

#### Scenario: Ports-check capacity counted separately
- **GIVEN** `agent_max_count` probe runs in progress and no ports-check runs in progress
- **WHEN** an agent requests a ports-check run
- **THEN** the capacity check passes because only `PortsCheck` runs are counted on that route

#### Scenario: Atomic oldest-run claim
- **GIVEN** multiple agents requesting concurrently
- **WHEN** each claims a test run
- **THEN** the oldest queued run for a bonded gateway is claimed exactly once via `SKIP LOCKED`, with ticket materials attached

### Requirement: The internal agent endpoints SHALL keep this exact request and response wire format

Both request endpoints MUST be `GET` with a JSON request body (unusual, but the shipped agent client sends `GET` with `Content-Type: application/json`), and the body MUST be `{ "payload": { "agent_public_key": [<32 numbers>], "timestamp": <unix seconds> }, "signature": [<64 numbers>] }` - on this surface ed25519 public keys and signatures are serialized as byte sequences (JSON arrays of numbers), NOT as base58 strings. The signature MUST be verified as ed25519 over `bincode::serialize(payload)`, so the payload's field order and types are part of the signing contract and cannot be reordered or extended without breaking existing agents.

A successful assignment MUST serialize the assignment fields flattened at the top level next to `ticket_materials`:

```json
{
  "testrun_id": 1,
  "assigned_at_utc": 1751894748,
  "gateway_identity_key": "<base58 ed25519>",
  "last_ports_check_utc": null,
  "ticket_materials": {
    "coin_indices_signatures":   [ { "data": [<bytes>], "revision": 1 } ],
    "expiration_date_signatures":[ { "data": [<bytes>], "revision": 1 } ],
    "master_verification_keys":  [ { "data": [<bytes>], "revision": 1 } ],
    "attached_tickets":          [ { "ticketbook": { "data": [<bytes>], "revision": 1 }, "usable_index": 0 } ]
  }
}
```

All ticket blobs MUST be JSON arrays of byte values, which makes these responses hundreds of kilobytes. `last_ports_check_utc` MUST be emitted, holding the unix seconds of the gateway's last persisted ports check or `null` when it has never had one; the agent-side type defaults it, so omitting the field would not break existing agents. All three submission endpoints MUST answer 201 Created with an empty body on success. The `/internal/testruns` router MUST accept bodies up to 5 MiB (exceeding it yields 413). The v1 submission endpoint MUST convert every JSON extractor rejection into 400 with the rejection text as the body, whereas the two v2 endpoints MUST surface axum's own rejections (415 for a missing or wrong `Content-Type`, 400 for malformed JSON, 422 for JSON that does not match the payload type). `{testrun_id}` MUST parse as `i32`, with a non-numeric segment rejected as 400.

#### Scenario: Assignment response is flattened
- **WHEN** an agent successfully requests a test run
- **THEN** `testrun_id`, `assigned_at_utc`, `gateway_identity_key` and `last_ports_check_utc` appear at the top level of the JSON object alongside `ticket_materials`, not nested under an `assignment` key

#### Scenario: Signature is over the bincode payload
- **GIVEN** a request whose JSON payload is valid but whose signature was computed over the JSON bytes
- **WHEN** it is received
- **THEN** verification fails and the API returns 401

#### Scenario: Successful submission returns an empty 201
- **WHEN** an agent submits results to any of the three submission endpoints
- **THEN** the response is 201 with no body

#### Scenario: Oversized submission
- **GIVEN** a probe submission whose body exceeds 5 MiB
- **WHEN** it is posted
- **THEN** the request is rejected with 413 and nothing is persisted

#### Scenario: Missing ports-check route tolerated by agents
- **GIVEN** an API deployment without the ports-check request route
- **WHEN** an agent polls `GET /internal/testruns/ports-check`
- **THEN** the 404 is treated by the agent as "endpoint unavailable, skip this iteration", so a replacement MUST NOT repurpose 404 on that path for other conditions

### Requirement: Probe result submission SHALL validate assignment identity and timestamp before completing

`POST /internal/testruns/{id}` (v1) MUST validate that the test run is in-progress and its `assigned_at_utc` matches the stored assignment timestamp, resolve the gateway, serialize the probe result, mark that run Complete, and update the gateway's last probe log/result and score, returning 201. Its rejection bodies MUST be `Testrun {id} not found in progress state (may be already completed or expired)` when no in-progress row matches, `Testrun {id} timestamp mismatch: expected {expected:?}, got {submitted}` on mismatch (with the expected value rendered as a Rust `Option` debug string, e.g. `Some(1751894748)`), and `Invalid probe_result` when the probe result cannot be re-serialized; a failure resolving the gateway MUST be 500.

`POST /internal/testruns/{id}/v2` MUST look the run up by id in **any** status (it does not require in-progress), MUST reject a submission whose `gateway_identity_key` differs from the stored gateway with 400 and the body `Gateway identity mismatch`, and MUST reject a timestamp mismatch with 400 and the body `Testrun timestamp mismatch: expected {expected:?}, got {submitted}`. When the id is unknown it MUST create the gateway if needed and insert an external `InProgress`/`Probe` run (marked with ip_address `external`) before processing. On success both v2 endpoints MUST complete **every** in-progress test run for that gateway rather than only the submitted id.

#### Scenario: Timestamp mismatch rejected
- **GIVEN** an in-progress test run whose stored `assigned_at_utc` differs from the submitted value
- **WHEN** results are submitted
- **THEN** the API returns 400 with the mismatch message and the run is not completed

#### Scenario: External result via v2
- **GIVEN** a submission for an unknown test-run id on the v2 endpoint
- **WHEN** it is received
- **THEN** the gateway is created if needed, an external in-progress run is inserted, and the result is processed to completion (201)

#### Scenario: Gateway identity mismatch on v2
- **GIVEN** a known test-run id whose gateway differs from the submitted `gateway_identity_key`
- **WHEN** results are submitted
- **THEN** the API returns 400 with the body `Gateway identity mismatch`

#### Scenario: Sibling in-progress runs completed
- **GIVEN** two in-progress test runs for the same gateway
- **WHEN** a v2 submission for one of them succeeds
- **THEN** both rows are marked Complete

### Requirement: Ports-check submission SHALL validate kind and persist only the compact result

`POST /internal/testruns/{id}/ports-check/v2` MUST, for a known test-run id, validate the kind, the gateway identity and the assignment timestamp in that order, rejecting with 400 and the bodies `Testrun {id} is not a ports-check run`, `Gateway identity mismatch` and `Ports-check testrun {id} timestamp mismatch: expected {expected:?}, got {submitted}` respectively. For an unknown id it MUST create the gateway if needed, insert an external `InProgress`/`PortsCheck` run, and process the submission without those checks. Processing MUST write the compact summary `{ all_pass, error, port_check_target, failed_ports }` plus `last_ports_check_utc` (server clock, not the submitted time) onto the gateway row, MUST mark only the submitted run Complete (by id, unlike the probe v2 path), and MUST NOT persist the probe log. It MUST return 201.

#### Scenario: Wrong kind rejected
- **GIVEN** a ports-check submission targeting a test run whose kind is Probe
- **WHEN** it is received
- **THEN** the API returns 400 with the body `Testrun {id} is not a ports-check run`

#### Scenario: Probe log not persisted for ports checks
- **WHEN** a ports-check result is submitted
- **THEN** only the compact ports-check JSON is stored and the probe log is discarded
