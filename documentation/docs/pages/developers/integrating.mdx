# Planning an integration

This page covers which of your endpoints to route through Nym, and what each of
those decisions costs. It applies to any runtime.

The unit of decision is the endpoint, not the application. Two failures follow
from ignoring that. One is a user flow that hangs because you never counted the
round trips inside it. The other is traffic that every code path says is routed,
but that never reaches the mixnet. Neither is a transport bug.

For the web-runtime reasons a policy fails to bind, see
[routing a browser or WebView app](/developers/browser-routing).

Two decisions come before this one. [What Nym cannot do](/developers/limitations)
tells you whether your workload fits.
[Choose a defence](/network/threat-model/choose-config) turns your threat model
into a network configuration. Settle both first.
</Callout>

## Which shape your integration has

Most of this page assumes [proxy mode](/developers#end-to-end-or-proxy): you
reach a third-party destination through an
[exit gateway](/network/infrastructure/exit-services). These failure modes come
from that case.

| Shape | What it means | How much of this page applies |
|---|---|---|
| [**Proxy**](/developers#end-to-end-or-proxy) | Your app reaches a third-party destination over the public internet, through an exit gateway. | All of it. |
| [**dVPN proxy**](/network/dvpn-mode) | The same shape, but [`nym-smoldvpn`](/developers/smoldvpn) carries the traffic over WireGuard instead of the mixnet. | Most of it. See [if you use the dVPN datapath](#if-you-use-the-dvpn-datapath). |
| [**End to end**](/network/threat-model/configurations/end-to-end) | Both ends run Nym. No exit gateway, no clearnet destination. | The flow arithmetic only. See [reaching another Nym client](#reaching-another-nym-client). |
| [**Service provider**](/developers/service-providers) | You run the service that others reach over Nym. | Almost none. See [when you are the destination](#when-you-are-the-destination). |

Every section that assumes a clearnet destination says so in its first line. A
section that does not say it applies to every shape.

## Routing is a per-endpoint decision

This section assumes a clearnet destination. End to end you decide nothing: you
reach the peer through Nym, or not at all.

Consider an app with three endpoints. The first sees an account identifier on
every request. That destination can link the identifier to an IP address, and
the mixnet exists to remove that link. Route it. The second serves public data
and sees no identifier. Routing it adds latency and hides nothing. The third
runs inside a third-party iframe, so your code cannot route it at all.

The transport played no part in any of those three answers. Each came from what
that destination already knows about the user, and from how the app reaches it.

## Profiling an endpoint before you route it

This section assumes a clearnet destination. End to end, the exit-facing
questions below have no equivalent.

Work through these questions for each endpoint. Any one of them can change the
answer on its own.

| Question | Why it decides the answer |
|---|---|
| **Does it see something that identifies this user?** An account address, an authenticated session, a device ID, an email. | This is the whole case for routing. A destination that sees no identifier gains nothing when you hide the IP address, because it has nothing to correlate. |
| **Is it HTTPS?** | The [exit gateway](/network/infrastructure/exit-services#ip-packet-router) reads plain HTTP in full. Routing an `http://` endpoint moves the observer. It does not remove it. |
| **Does a user wait on it?** A request that blocks a screen, against a background refresh. | Latency is [the mechanism](/developers/limitations#latency-is-the-mechanism), not a shortfall you can tune away. Deferred work absorbs it. A call in front of a user does not. |
| **Is it called in sequence with others?** | Sequential dependent calls multiply the cost. No single request reveals this. See below. |
| **Can you reach its transport at all?** | Third-party frames, vendor SDKs and libraries that do their own networking stay outside your control, whatever your policy says. |

Route the smallest set that identifies users over HTTPS, then widen it. Starting
broad means debugging the routing underneath a UI that already hangs.

## Sequential dependent calls multiply latency

One routed request that takes a second is fine. A flow issuing three dependent
requests inside a single user action pays that second three times over, in
series. Add the tunnel bring-up if the tunnel was cold.
From the outside, one button appears to do nothing for many seconds. No request
timed out, none errored, and none was unreasonable on its own.

The cost belongs to the flow, not to any request inside it. Profiling endpoints
one at a time never surfaces it. Walk your user journeys and count the round
trips in each, then restructure or defer any journey with more than one
dependent routed call.

## Warm the tunnel before the first request

Work that happens once dominates cold start. It brings up the client and
completes the gateway handshake. If the destination is on the clearnet, it then
adds DNS, TCP and TLS through the tunnel. Whoever triggers this waits for all of
it, and blames your application.

Bring the tunnel up ahead of use, then send one warm-up request before the app
starts querying. This moves the expensive part away from someone who is waiting,
and leaves the tunnel warm for everything after it.

Read timings with retries in mind. The client retries a failed connection on its own,
and a retry that succeeds never surfaces as an error. A request several times
slower than its neighbours may be one silent reconnection, so turn debug logging
on before you tune against a slow sample.

## Bound concurrent requests, but do not serialise them

Concurrency fails in the opposite direction to sequential calls. Issue several
requests at once and each one misses the connection pool, because a pool only
helps after a connection returns to it. Each one opens its own connection, and
under [proxy mode](/developers#end-to-end-or-proxy) its own TLS handshake
through the mixnet. You pay setup once per call. Libraries that batch or
parallelise on your behalf do this on their own.

A strict queue overcorrects. One stalled request then blocks everything behind
it for the full timeout, where the rest would otherwise have gone through. A
small concurrency limit with a per-request bound is the shape to aim for. Pick
the bound in both directions: too generous and a stuck request holds the UI, too
tight and you abandon requests that would have completed.

End to end the same bound applies for a different reason. Replies arrive on
[single-use reply blocks](/network/mixnet-mode/anonymous-replies) that your
client computed and sent in advance, so outstanding requests are reply capacity
you already spent.

<Callout type="warning">
Check what your timeout does. In the browser packages it is a race that bounds
*your* wait. The underlying request continues inside the worker, and you cannot
cancel it (see
[timeouts and cancellation](/developers/mix-fetch/guides#timeouts-and-cancellation)).
The bound abandons the request rather than cancelling it, so a retry on timeout
leaves two requests in flight.
</Callout>

## Make the privacy flag announce itself unconditionally

Gate every log line on the feature flag, and "switched off" produces the same
output as "never ran". That distinction is the one thing you need when you ask
where a user's traffic went, and gated logging throws it away.

Log the resolved configuration at startup, whatever the flag says: the values as
read, the routed set as parsed, and the failure policy in force. It separates an
integration that ran and did nothing from one you never switched on.

## Decide fail-open or fail-closed explicitly

This section assumes a clearnet destination. A direct path to the same
destination is what makes the choice possible, and no direct path reaches a Nym
address.

When the tunnel is unavailable, the app either refuses the request or falls back
to the clearnet. Fail-open gives the better user experience and the worse
privacy outcome. Fail-closed reverses that.

Whichever you pick, pick it. The failure is deciding by accident: a `catch`
written for another purpose chooses fail-open for you, and so does a retry
helper three layers down. An integration whose leak detection raises, while its
transport retries over the clearnet, has shipped fail-open, whatever the
setting says.

## Prove the traffic went through the mixnet

This section assumes a clearnet destination. All three levels below test whether
a request took the tunnel instead of a direct path. End to end, no direct path
reaches the peer.

A routing policy written in application code states an intent. Put something
underneath it that raises an error when the intent is wrong.

| Level | What it does | What it cannot tell you |
|---|---|---|
| **Detection** | Traps requests that reach a routed destination by a path the policy does not control, and reports them as bugs. | Whether the mixnet did anything. It only proves that your code ran. |
| **Positive proof** | Asks one echo service over both paths, and compares the source address it saw each time. | Whether anything else leaks. It tests a single request. |
| **Enforcement** | Removes the direct path at the platform level. A request that succeeds can then only have come through the tunnel. | Anything the platform does not govern, such as another process or an embedded third-party context. |

Only positive proof separates "the request went through the tunnel" from "our
transport code ran without throwing". All three levels are platform-specific.
For the browser mechanics, see
[routing a browser or WebView app](/developers/browser-routing).

## Choose the resolver

This section assumes a clearnet destination. End to end there is no DNS: you
address a Nym client by its [key](/network/reference/addressing), not by a name.

DNS lookups travel through the tunnel and exit with everything else. The
resolver sees queries that arrive from the exit gateway, not from your user, and
that much is the property you wanted. It does not stop the resolver seeing every
hostname your app looks up, and the default is a large public resolver.

Decide whether that suits your users, instead of inheriting it. `primaryDns` and
`fallbackDns` change it. [mix-dns](/developers/mix-dns/guides) has the format.

## What the integration gets you, and what it does not

This section assumes a clearnet destination. End to end the assessment differs,
because no third-party destination exists to take the view away from. See
[end to end](/network/threat-model/configurations/end-to-end).

Routing your endpoints is
[Layer 1](/network/threat-model/two-layer-model) and only Layer 1. The
destination stops seeing the user's IP address, which closes
[V1](/network/threat-model/vectors) against it. The mixnet leaves timing and
content untouched, which keeps [V2 and V3](/network/threat-model/vectors) open
and hands them to [your application](/developers/swizzle). Any identifier your
requests already carry still identifies the user, and traffic you could not
route still shows the real address.

For most applications the destination is the
[primary adversary](/network/threat-model/actors#l2-is-the-primary-adversary-for-most-applications),
so this is a real win against one vector of three. Say both halves of that to
whoever signs the work off.

## If you use the dVPN datapath

[`nym-smoldvpn`](/developers/smoldvpn) reaches a clearnet destination like any
other proxy integration, so this page applies to it. It carries your traffic
over a WireGuard [dVPN](/network/dvpn-mode) instead of the mixnet, which changes
three things.

Latency is much lower, so the flow arithmetic hurts less. Cold start and
sequential round trips still cost what they cost. The mixnet parts of this page
do not apply, because dVPN mode sends no Sphinx packets and uses no reply
blocks.

dVPN mode provides **no in-transit timing protection**. It hides the client IP
address from the destination and splits trust across two operators, and closes
nothing else.

## Reaching another Nym client

When both ends run Nym, there is no exit gateway and no clearnet destination.
Traffic stays inside the mixnet the whole way, the peer never learns your IP
address, and replies come back on reply blocks that you supplied. This removes
the untrusted destination instead of hiding your address from it, so the
assessment differs. See
[end to end](/network/threat-model/configurations/end-to-end).

The flow arithmetic carries over. Round trips inside one user action still cost
what they cost. Cold start still lands on whoever triggers it, and outstanding
requests still need a bound.

Everything that needs an exit or a direct path does not carry over. That covers
the routing decision, the HTTPS question, connection pooling, the resolver,
fail-open, and proving that the traffic took the tunnel.

<Callout type="info">
The failure modes on this page come from clearnet-exit integrations. No
equivalent list exists yet for client-to-client work.
</Callout>

## When you are the destination

If you run the service that others reach over Nym, the planning problem inverts.
You never open an outbound connection. Your address is
[only as stable as its gateway](/developers/service-providers#your-address-is-only-as-stable-as-its-gateway).
Every reply you send spends one of the sender's reply blocks, out of a fixed
per-second budget. See
[building a Nym service provider](/developers/service-providers).
