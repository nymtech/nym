# node-status-api-persistence Specification

> Generated by openlore on 2026-07-07
> Revised 2026-08-03: reverse-engineered from the implementation to capture the actual schema and query semantics (column types, uniqueness, refresh patterns, retention), because a replacement API must read and write the same database without changing what consumers see.
> Source files: `nym-node-status-api/nym-node-status-api/src/db/{mod,models}.rs`, `db/queries/{gateways,gateways_stats,nym_nodes,node_families,packet_stats,scraper,summary,testruns,ecash_data,misc}.rs`, `migrations_pg/*.sql`, `cli/mod.rs`

## Purpose

Defines the PostgreSQL persistence layer of the node status service: pool setup and migrations, the table inventory and its ownership, and the query semantics that the HTTP API and background workers depend on. The store is the only contract between the workers of [[node-status-api-monitoring]] and the read API of [[node-status-api-http]], so its uniqueness constraints, refresh patterns and retention behaviour are part of the compatibility surface.

## Requirements

### Requirement: Storage SHALL initialise a PostgreSQL pool and run the embedded migrations

`Storage::init` MUST build a `sqlx` PostgreSQL pool from `DATABASE_URL` with `sqlx_max_connections` (default 20), `sqlx_min_connections` (default 5) and `sqlx_busy_timeout_s` acquire timeout (default 5s), and MUST disable statement logging. When `PG_CERT` is set it MUST switch the connection to `sslmode=require` with that file as the root certificate. It MUST then run the migrations embedded at compile time from `./migrations_pg` unless `SKIP_MIGRATIONS` is set to exactly the string `true` (any other value, including `1` or `TRUE`, still runs them). Postgres MUST be the only supported engine: all queries are compile-time-checked `sqlx` macros against it.

#### Scenario: Migrations run on init
- **GIVEN** a reachable database and `SKIP_MIGRATIONS` unset
- **WHEN** `Storage::init` runs
- **THEN** the pool is built and the `./migrations_pg` migrations are applied

#### Scenario: Migrations skipped only on the exact value
- **GIVEN** `SKIP_MIGRATIONS=1`
- **WHEN** `Storage::init` runs
- **THEN** migrations still run, because only the literal `true` disables them

### Requirement: Each table SHALL have documented writers, column ownership, and these type choices

The store MUST consist of these tables with these writers. Most tables have a single writer; `gateways` has three, and their ownership MUST be understood at column level rather than table level, because they interleave without any cross-writer coordination:

- the monitor owns `bonded`, `self_described`, `explorer_pretty_bond`, `performance` (whole-table refresh per cycle);
- test-run submission owns `last_probe_result`, `last_probe_log`, `ports_check`, `last_ports_check_utc`, `last_testrun_utc`;
- the packet-stats scraper owns `bridges`;
- `last_updated_utc` is the one shared column, written by both the monitor refresh and test-run submission, so it means "either snapshot or probe touched this row" rather than any single event.

Each writer MUST use its own transaction, so a reader can observe a row whose snapshot columns are from one cycle and whose probe columns are from a different test run. That interleaving is by design and MUST NOT be assumed atomic.

| Table | Written by | Read by |
| --- | --- | --- |
| `gateways` | monitor (snapshot), test-run submission (probe result/log, ports check, test-run timestamps), packet-stats scraper (bridges) | gateway + dVPN + services read paths |
| `gateway_description` | description scraper (entry/exit nodes) | `/v2/gateways` join |
| `nym_nodes` | monitor (snapshot) | dVPN + explorer read paths, both scrapers' work queue |
| `nym_node_descriptions` | description scraper | explorer read path |
| `nym_nodes_packet_stats_raw` | packet-stats scraper | daily-delta baseline only |
| `nym_node_daily_mixing_stats` | packet-stats scraper | `/v2/mixnodes/stats` |
| `node_families`, `node_family_members` | monitor (snapshot replace) | dVPN + explorer family enrichment |
| `gateway_session_stats` | metrics scraper | `/v2/metrics/sessions` |
| `summary`, `summary_history` | monitor | `/v2/summary`, `/v2/summary/history` |
| `testruns` | test-run queuer, ports-check scheduler, agent submissions | assignment + completion |
| `ecash_ticketbook`, `distributed_partial_ticketbook`, and the other ecash tables | ticketbook manager | test-run assignment |
| `mixnodes`, `mixnode_description`, `mixnode_daily_stats`, `mixnode_packet_stats_raw` | nothing (legacy, retained) | `mixnodes.historical.count` only |

The following type choices MUST be preserved because reads and writes depend on them: `nym_nodes.performance` is a `VARCHAR` holding the decimal string form of a percent (parsed back as a `Percent`); `nym_nodes.{ip_addresses,node_role,supported_roles,entry,self_described,bond_info}` and `gateways.{ports_check,bridges}` are `JSONB` while `gateways.{self_described,explorer_pretty_bond,last_probe_result,last_probe_log}` remain `VARCHAR` holding JSON **text**; `gateways.self_described` is `NOT NULL`; timestamps are split between `BIGINT` (`gateways`, `summary`, `summary_history`, `testruns`, families) and `INTEGER` (`nym_nodes.last_updated_utc`, `nym_node_descriptions.last_updated_utc`, `nym_nodes_packet_stats_raw.timestamp_utc`), which truncates in 2038; `gateway_session_stats.day` is a real `DATE`; `nym_node_daily_mixing_stats.date_utc` and `summary_history.date` are `VARCHAR` holding `YYYY-MM-DD`.

The scoring columns on `gateways` (`routing_score`, `config_score`, `routing_score_successes/samples`, `config_score_successes/samples`, `test_run_samples`) MUST be treated as dead: nothing writes them any more, so they hold their schema default of `0`, and the helper still named `update_gateway_score` only stamps `last_testrun_utc` and `last_updated_utc` after a submission. This is why the read path reports `routing_score: 0.0` and `config_score: 0` unconditionally.

Uniqueness MUST be: `gateways.gateway_identity_key` unique; `nym_nodes.node_id` primary key with the identity/sphinx-key unique constraints deliberately dropped; `node_family_members.node_id` **primary key**, which enforces that a node belongs to at most one family; `gateway_session_stats (node_id, day)` unique; `nym_node_daily_mixing_stats (node_id, date_utc)` unique; `summary.key` primary key; `summary_history.date` unique. Foreign keys from the description, raw-stats and daily-stats tables to `nym_nodes` MUST cascade on delete, though nothing ever deletes a `nym_nodes` row so the cascade never fires in practice.

#### Scenario: A node cannot join two families
- **GIVEN** a families snapshot listing the same node in two families
- **WHEN** the members batch is inserted
- **THEN** the insert violates the `node_id` primary key and the whole snapshot transaction aborts

#### Scenario: Performance survives a round trip
- **GIVEN** a node whose performance is written as its decimal string form
- **WHEN** the row is read back into a skimmed node
- **THEN** the string parses back into the same percent, and an unparsable value makes that node's conversion fail and be skipped

### Requirement: Directory snapshots SHALL be refreshed with a null-then-upsert pattern inside one transaction

Refreshing `nym_nodes` MUST, in one transaction, first set `self_described = NULL` and `bond_info = NULL` on **all** rows and then upsert the present nodes, so a node absent from the latest directory keeps its row but is excluded from every "described and bonded" read. Refreshing `gateways` MUST, in one transaction, first set `bonded = false` on all rows and then upsert the present gateways. It MUST NOT clear a departed gateway's `self_described`, `explorer_pretty_bond`, `last_probe_result` or `ports_check`, so those keep serving their last known values alongside `bonded=false`. Node families MUST be refreshed by deleting `node_families` (cascading to members) and re-inserting both tables via two `UNNEST` batch inserts in the same transaction, so reads never observe a partial snapshot.

#### Scenario: Departed gateway marked unbonded but retained
- **GIVEN** a gateway present in a prior snapshot and absent from the current directory
- **WHEN** the gateway snapshot is refreshed
- **THEN** the row ends the transaction with `bonded=false` while its stored probe result and self-description remain readable

#### Scenario: Departed node drops out of described reads
- **GIVEN** a node absent from the current directory
- **WHEN** the nym-nodes snapshot is refreshed
- **THEN** its `self_described` and `bond_info` are `NULL`, so it disappears from the explorer list, the dVPN build and both scraper queues

#### Scenario: Families snapshot is atomic
- **WHEN** the families snapshot is replaced
- **THEN** concurrent readers see either the whole previous snapshot or the whole new one

### Requirement: Daily packet deltas SHALL be derived from the previous scrape read inside the same transaction

Per scraped node, the batch store MUST insert the raw counter row **before** computing the daily delta, and the delta baseline MUST be read as the second-most-recent raw row for that node (`ORDER BY timestamp_utc DESC LIMIT 1 OFFSET 1`) within the same transaction - the just-inserted row being the most recent is what makes `OFFSET 1` mean "the previous scrape". This ordering MUST be preserved. When no baseline row exists the deltas MUST be zero. When a counter has decreased since the baseline (a node restart) the current value MUST be used instead of a negative delta. The daily row MUST be upserted on `(node_id, date_utc)` accumulating the three packet counters and overwriting `total_stake`, where `total_stake` is read from `nym_nodes` with `fetch_one` (so a node missing from `nym_nodes` aborts the whole batch transaction). Raw counter rows MUST be append-only, with no deduplication and no upsert.

#### Scenario: First ever scrape yields zero deltas
- **GIVEN** a node with no prior raw stats row
- **WHEN** its first scrape is stored
- **THEN** the raw row is written and the daily row records zero received/sent/dropped

#### Scenario: Daily stats accumulate on conflict
- **GIVEN** an existing daily row for a node and date
- **WHEN** a new delta is stored for the same date
- **THEN** the packet counters are summed and the stake is overwritten, without duplicating the row

#### Scenario: Restart does not produce a negative delta
- **GIVEN** a node whose counter is lower than the baseline row
- **WHEN** the delta is computed
- **THEN** the current value is used as the delta

### Requirement: Session stats SHALL be immutable per node-day and read without an order

Session rows MUST be inserted with `ON CONFLICT DO NOTHING` against the `(node_id, day)` uniqueness constraint, so the first successful write for a node-day is final and later data for that day is silently dropped. The duration arrays and user hashes MUST be stored as JSON **text** columns (`NULL` when empty) and MUST be parsed back leniently on read, with an unparsable value becoming `null` rather than failing the request. The read query MUST NOT impose an `ORDER BY`, so the order of `/v2/metrics/sessions` items - and therefore its pagination - is whatever Postgres returns and is not stable across cache refills.

#### Scenario: Second write for the same day is a no-op
- **GIVEN** an existing row for a node and day
- **WHEN** the same node-day is inserted again
- **THEN** the insert does nothing and the stored row is unchanged

#### Scenario: Unstable pagination
- **GIVEN** two consecutive cache refills of the session-stats list
- **WHEN** the same `page`/`size` is requested against each
- **THEN** the returned items may differ, because the underlying query defines no order

### Requirement: Retention SHALL be limited to two deletions, leaving the remaining tables unbounded

The only rows the service ever deletes at runtime MUST be the `node_families`/`node_family_members` snapshot (replaced each monitor cycle) and `gateway_session_stats` rows whose `day` is at or before one year ago. Every other table MUST grow without bound: `nym_nodes_packet_stats_raw` gains a row per node per hourly scrape, `nym_node_daily_mixing_stats` gains a row per node per day, `testruns` retains every completed run, and `gateways`, `mixnodes` and `nym_nodes` retain rows for nodes that have left the network. The all-time size of `gateways` and `mixnodes` MUST remain observable through the `gateways.historical.count` and `mixnodes.historical.count` summary keys, which are literal `count(id)` reads over those tables.

#### Scenario: Old raw stats are never pruned
- **GIVEN** a year of hourly packet-stats scrapes
- **WHEN** the service continues running
- **THEN** every raw counter row is still present, since only sessions and the families snapshot are ever deleted

#### Scenario: Sessions pruned at one year
- **GIVEN** session rows older than one year
- **WHEN** a metrics-scraper cycle finishes storing
- **THEN** those rows are deleted

### Requirement: Concurrent claims SHALL use row locking, with different strategies per resource

Test-run assignment MUST claim work with a CTE that selects the oldest queued run of the requested kind joined to a bonded gateway with performance > 0 `FOR UPDATE ... SKIP LOCKED`, and MUST flip its status to in-progress and stamp `last_assigned_utc` in the same statement, so concurrent agents never receive the same run. Spending a ticketbook MUST be a single `UPDATE ... SET used_tickets = used_tickets + 1 WHERE id = (SELECT ... ORDER BY expiration_date ASC LIMIT 1 FOR UPDATE)` statement that returns the claimed book, taking the soonest-expiring usable one; unlike test-run assignment it MUST NOT use `SKIP LOCKED`, so simultaneous claimants queue on the same candidate row instead of moving to the next.

#### Scenario: Two agents cannot claim the same test run
- **GIVEN** two concurrent assignment queries
- **WHEN** both execute
- **THEN** `SKIP LOCKED` makes each claim a different queued run, or one receives none

#### Scenario: Ticket claims serialize
- **GIVEN** two concurrent ticket claims for the same ticket type
- **WHEN** both execute
- **THEN** they serialize on the same soonest-expiring row rather than skipping it, and each ends up with a distinct usable index

### Requirement: Summary reads SHALL require the full set of summary keys

`get_summary` MUST validate that all eight summary keys are present and MUST return an internal-error result if any is missing, rather than a partial `NetworkSummary`. Counts MUST be parsed from the stored text with a `0` fallback, and each block's `last_updated_utc` MUST be rendered from the `last_updated_utc` column of its own source row.

#### Scenario: Missing summary key
- **GIVEN** the `summary` table is missing one required key
- **WHEN** `get_summary` runs
- **THEN** it returns an internal error and logs which keys were missing

### Requirement: The scraping work queue SHALL classify nodes by bonded-gateway identity

`get_nodes_for_scraping` MUST return only nodes whose `nym_nodes` row has both `self_described` and `bond_info` set, MUST convert each to a skimmed node (skipping and logging rows that fail conversion), and MUST classify a node as an entry/exit nym-node when its base58 ed25519 identity appears among the identities of `bonded = true` gateways, otherwise as a mixing nym-node. Descriptions for entry/exit nodes MUST be written to both `nym_node_descriptions` and `gateway_description`; because the latter has a foreign key to `gateways.gateway_identity_key`, the gateway row must already exist for that write to succeed.

#### Scenario: Gateway node written to both description tables
- **GIVEN** a scraped node whose identity matches a bonded gateway
- **WHEN** its description is stored
- **THEN** it is written to both the nym-node and gateway description tables

#### Scenario: Undescribed or unbonded node is not scraped
- **GIVEN** a node whose `self_described` or `bond_info` is `NULL`
- **WHEN** the scraping queue is built
- **THEN** the node is absent from it

### Requirement: Stored ports-check payloads SHALL be normalised on read and were migrated out of the probe result

The `gateways.ports_check` JSONB column MUST be served in the canonical four-key form `{ all_pass, error, port_check_target, failed_ports }`, normalising on read both the legacy dedicated shape `{ can_register, port_check_target, ports, error }` (deriving `all_pass` as "can register, at least one port tested, and no failed port") and the intermediate shape carrying `ports_tested`. A `null` JSON value MUST be treated as absent. This column MUST be understood as historically extracted out of `last_probe_result` by migration: the extraction is row-by-row and skips rows whose stored probe text is not valid JSON, so some gateways legitimately have `ports_check = NULL` with ports data still embedded in their raw probe text.

#### Scenario: Legacy payload normalised on read
- **GIVEN** a gateway whose stored `ports_check` uses the legacy shape with one closed port
- **WHEN** the gateway is read
- **THEN** the response carries `all_pass: false` and that port listed in `failed_ports`

#### Scenario: Unparsable probe text left behind by the migration
- **GIVEN** a gateway whose `last_probe_result` is truncated non-JSON text containing ports data
- **WHEN** the extraction migration runs
- **THEN** the row is skipped and its `ports_check` stays `NULL`

## Technical Notes

- **Implementation**: `db/mod.rs` (`Storage::init`, pool, `MIGRATOR`), `db/models.rs` (DTOs and insert records, `TestRunStatus`/`TestRunKind`, `NymNodeInsertRecord::new`, `ScraperNodeInfo::contact_addresses`, ports-check normalisation, self-described de-helpers with `#[serde(default)]` for forward compatibility), `db/queries/*` (one module per table area), `migrations_pg/*.sql` (18 migrations; the schema is the accumulated result, including SQLite-era leftovers).
- **Engine**: PostgreSQL only, via `sqlx` with compile-time-checked macros; migrations embedded via `sqlx::migrate!("./migrations_pg")`.
- **Legacy surface**: the `mixnodes*` tables are no longer written by any worker; they survive only so `mixnodes.historical.count` keeps reporting a number, and `/v2/mixnodes/stats` reads the nym-node daily table despite its name.
- **Hazards for a replacement**: `INTEGER` timestamp columns (2038), the append-only raw-stats and never-pruned testruns tables, the `OFFSET 1` delta baseline that depends on insert ordering within the transaction, first-write-wins session rows, unordered session reads, `node_family_members.node_id` as a primary key, and JSON stored as text in `gateways` versus JSONB in `nym_nodes`.
- **Related specs**: written by [[node-status-api-monitoring]], [[node-status-api-testruns]], [[node-status-api-ticketbook]]; read by [[node-status-api-http]].
