# Planning an integration

Most integrations start from one sentence: send the app's traffic through Nym.
That is rarely one change. It goes wrong in the same order every time. First a
user flow hangs, because nobody counted the round trips inside it. Then it turns
out that some traffic never went through Nym, although every code path suggested
it did. Neither is a transport bug. Both come from one assumption: that an
application has a single point where traffic leaves.

This page is about what to route, and what that decision costs. It applies to
any runtime. For the browser-specific ways a routing policy fails to bind, see
[routing a browser or WebView app](/developers/browser-routing).

<Callout type="info">
Two decisions come before this one. [What Nym cannot do](/developers/limitations)
tells you whether your workload fits. [Choose a defence](/network/threat-model/choose-config)
turns your threat model into a network configuration. This page assumes that you
settled both.
</Callout>

## Which shape your integration has

Most of this page assumes that you reach a **clearnet destination**. That is a
third-party server which does not run Nym. You reach it through an
[exit gateway](/network/infrastructure/exit-services). The rest of the developer
docs call this **proxy mode**. It is the common case, and these failure modes
come from it.

| Shape | What it means | How much of this page applies |
|---|---|---|
| **Proxy (clearnet exit)** | Your app reaches a third-party server over the public internet, through an exit gateway. | All of it. |
| **dVPN proxy** | The same shape, but [`nym-smoldvpn`](/developers/smoldvpn) carries the traffic over WireGuard instead of the mixnet. | Most of it. See [if you use the dVPN datapath](#if-you-use-the-dvpn-datapath). |
| **End-to-end (client to client)** | Both ends run Nym. No exit gateway, no clearnet destination. | The flow arithmetic only. See [reaching another Nym client](#reaching-another-nym-client). |
| **You are the destination** | You run the service that others reach over Nym. | Almost none. See [when you are the destination](#when-you-are-the-destination). |

Every section that assumes a clearnet destination says so in its first line. A
section that does not say it applies to every shape.

## Routing is a per-endpoint decision

This section assumes a clearnet destination. End to end you decide nothing: you
reach the peer through Nym, or not at all.

Consider an app with three endpoints. The first sees an account identifier on
every request. That destination can link the identifier to an IP address, and
the mixnet exists to remove exactly that. So route it. The second serves public
data and sees no identifier. Routing it adds latency and hides nothing. The
third runs inside a third-party iframe, so your code cannot route it at all.

Three endpoints, three answers, one transport. The transport decided none of
them. Two things decided them: what each destination already knows about the
user, and how the app reaches it.

The unit of decision is therefore the endpoint. Planning produces a list of them.

## Profiling an endpoint before you route it

This section assumes a clearnet destination. End to end, the exit-facing
questions below have no equivalent.

Work through these questions for each endpoint. Any one of them can change the
answer on its own. This is why you cannot reason about the application as a
whole.

| Question | Why it decides the answer |
|---|---|
| **Does it see something that identifies this user?** An account address, an authenticated session, a device ID, an email. | This is the whole case for routing. A destination that sees no identifier gains nothing when you hide the IP address, because it has nothing to correlate. |
| **Is it HTTPS?** | The [exit gateway](/network/infrastructure/exit-services#ip-packet-router) reads plain HTTP in full. Routing an `http://` endpoint moves the observer. It does not remove it. |
| **Does a user wait on it?** A request that blocks a screen, against a background refresh. | Latency is [the mechanism](/developers/limitations#latency-is-the-mechanism), not a shortfall you can tune away. Deferred work absorbs it. A call in front of a user does not. |
| **Is it called in sequence with others?** | Sequential dependent calls multiply the cost. No single request reveals this. See below. |
| **Can you reach its transport at all?** | Third-party frames, vendor SDKs and libraries that do their own networking stay outside your control, whatever your policy says. |

Route the smallest set that identifies users over HTTPS. Then widen it. A narrow
set that works beats a broad set that you must debug underneath a hanging UI.

## Sequential calls in one user action are the usual failure

A single routed request is not where the cost shows up.

One routed request that takes a second is fine. Now take a flow that issues
three dependent requests inside a single user action. It pays that second three
times over, in series. It also pays the tunnel bring-up, if the tunnel was cold.
From the outside, one button appears to do nothing for many seconds. No request
timed out. None errored. None was individually unreasonable.

The cost belongs to the flow, not to any request inside it. Profiling endpoints
one at a time therefore never surfaces it. Walk your user journeys and count the
round trips in each. Restructure or defer any journey with more than one
dependent routed call. Where the destination is on the clearnet, you can also
leave it unrouted until the tunnel is warm.

## Concurrent requests each pay their own handshake

This section assumes a clearnet destination, where the tunnel carries TCP and
TLS for you.

The opposite arrangement fails differently. Issue several calls at once. Each
one misses the connection pool, because a pool only helps after a connection
returns to it. Each one therefore opens its own connection and its own TLS
handshake through the mixnet. You pay setup once per call, instead of
amortising it across the batch.

Libraries that batch or parallelise on your behalf do this without being asked.
Find out which of your dependencies do.

## Warm the tunnel before the first request

Cold start is dominated by work that happens once. That work has nothing to do
with the request that triggered it. It brings up the client and completes the
gateway handshake. If the destination is on the clearnet, it then adds DNS, TCP
and TLS through the tunnel. Whoever triggers this waits for all of it, and
blames your application.

Bring the tunnel up ahead of use. Then send one warm-up request before the app
starts querying. This moves the expensive part away from someone who is waiting,
and it leaves the tunnel warm for everything after it.

## Bound requests, but do not serialise them to one

The obvious response to the concurrency problem is a strict queue. It
overcorrects. One stalled request now blocks everything behind it for the full
timeout. Without the queue, the rest would have gone through. A frozen app is
worse than a slow one.

A small concurrency limit, with a per-request bound, is the shape to aim for.
Pick the bound deliberately in both directions. Too generous, and a
stuck request holds the UI. Too tight, and you abandon requests that would have
completed.

End to end, the same bound earns its place for a different reason. Replies
arrive on single-use reply blocks. Your client computes and sends those blocks
in advance. Outstanding requests are therefore reply capacity that you already
spent. See [anonymous replies](/network/mixnet-mode/anonymous-replies) for
replenishment.

<Callout type="warning">
Check what your timeout does. In the browser packages it is a race that bounds
*your* wait. The underlying request continues inside the worker, and you cannot
cancel it (see
[timeouts and cancellation](/developers/mix-fetch/guides#timeouts-and-cancellation)).
The bound abandons the request rather than cancelling it, so a retry on timeout
leaves two requests in flight.
</Callout>

## Make the privacy flag announce itself unconditionally

Gate every log line on the feature flag, and "switched off" produces the same
output as "never ran". That distinction is the one thing you need when you ask
where a user's traffic went. Gated logging destroys it. Silence must mean
something specific.

Log the resolved configuration at startup, whatever the flag says: the values as
read, the routed set as parsed, and the failure policy in force. It costs a few
lines. It also separates an integration that ran and did nothing from one that
nobody switched on.

## Decide fail-open or fail-closed explicitly

This section assumes a clearnet destination. A direct path to the same server is
what makes the choice possible, and no direct path reaches a Nym address.

When the tunnel is unavailable, the app either refuses the request or falls back
to the clearnet. Fail-open gives the better user experience and the worse
privacy outcome. Fail-closed reverses that.

Whichever you pick, pick it. What goes wrong is deciding by accident. A `catch`
written for another purpose chooses fail-open for you. So does a retry helper
three layers down. Nothing reports that it happened. An integration whose leak
detection raises, while its transport quietly retries over the clearnet, has
shipped fail-open, whatever the setting says.

## Prove the traffic went through the mixnet

This section assumes a clearnet destination. All three levels below test whether
a request took the tunnel instead of a direct path. End to end, no direct path
reaches the peer.

A routing policy written in application code is a statement of intent. Put
something underneath it that fails loudly. Here are three levels, weakest to
strongest. Each catches what the others miss.

| Level | What it does | What it cannot tell you |
|---|---|---|
| **Detection** | Traps requests that reach a routed destination by a path the policy does not control, and reports them as bugs. | Whether the mixnet did anything. It only proves that your code ran. |
| **Positive proof** | Asks one echo service over both paths, and compares the source address it saw each time. | Whether anything else leaks. It tests a single request. |
| **Enforcement** | Removes the direct path at the platform level. A request that succeeds can then only have come through the tunnel. | Anything the platform does not govern, such as another process or an embedded third-party context. |

Positive proof is the only level that separates "the request went through the
tunnel" from "our transport code ran without throwing". All three levels are
platform-specific. For the browser
mechanics, see [routing a browser or WebView app](/developers/browser-routing).

## Read timings with retries in mind

Clients retry a failed connection internally. A retry that succeeds never
surfaces as an error. A request several times slower than its neighbours may be
one silent reconnection rather than mixnet latency. Turn debug logging on before
you tune anything against a slow sample.

## Set the resolver deliberately

This section assumes a clearnet destination. End to end there is no DNS: you
address a Nym client by its key, not by a name.

DNS lookups travel through the tunnel and exit with everything else. The
resolver therefore sees queries that arrive from the exit gateway, not from your
user. That much is the property you wanted. It does not stop the resolver seeing
every hostname your app looks up, and the default is a large public resolver.

Decide whether that suits your users, instead of inheriting it. `primaryDns` and
`fallbackDns` change it. [mix-dns](/developers/mix-dns/guides) has the format.

## What the integration gets you, and what it does not

This section assumes a clearnet destination. End to end the assessment differs,
because no third-party server exists to take the view away from. See
[end to end](/network/threat-model/configurations/end-to-end).

The resulting property is narrower than "the app is now private". In the
vocabulary of the [two-layer model](/network/threat-model/two-layer-model),
routing your endpoints is Layer 1 and only Layer 1:

- **The destination stops seeing the user's IP address.** That is V1 identity
  protection against the destination. It is the whole of what the transport buys
  you here.
- **Timing and content are untouched.** The destination still sees when every
  request arrives, and everything each one contains. Mixing changes what a
  network observer can infer. It does nothing about the server you talk to. That
  is V2 and V3, that is Layer 2, and it belongs to
  [your application](/developers/swizzle).
- **Requests stay linkable.** Any identifier your requests already carry still
  identifies the user. A session that holds one exit for its lifetime also
  presents a stable exit address.
- **Unroutable traffic is unchanged.** Third-party contexts still see the real
  address.

For most applications the destination is the
[primary adversary](/network/threat-model/actors#l2-is-the-primary-adversary-for-most-applications).
Taking its view of the user's IP address away is a real win. It is also one
vector of three. Say both halves of that to whoever signs the work off.

## If you use the dVPN datapath

[`nym-smoldvpn`](/developers/smoldvpn) reaches a clearnet destination like any
other proxy integration, so this page applies to it. It carries your traffic
over a WireGuard dVPN instead of the mixnet, which changes three things.

Latency is much lower, so the flow arithmetic hurts less. It does not disappear:
cold start and sequential round trips still cost what they cost. The mixnet
parts of this page do not apply, because dVPN mode sends no Sphinx packets and
uses no reply blocks. Most importantly, dVPN mode provides **no in-transit
timing protection**. It hides the client IP address from the destination and
splits trust across two operators. It closes nothing else.

Read [dVPN mode](/network/dvpn-mode) before you choose it. It is a different
product, not a faster mixnet.

## Reaching another Nym client

When both ends run Nym, there is no exit gateway and no clearnet destination.
Traffic stays inside the mixnet the whole way. The peer never learns your IP
address, and replies come back on reply blocks that you supplied. This removes
the untrusted destination, rather than hiding your address from it, so the
assessment differs. See
[end to end](/network/threat-model/configurations/end-to-end).

The flow arithmetic carries over from this page. Round trips inside one user
action still cost what they cost. Cold start still lands on whoever triggers it.
Outstanding requests still need a bound.

Everything that needs an exit or a direct path does not carry over. That covers
the routing decision itself, the HTTPS question, connection pooling, the
resolver, and fail-open. It also covers the whole of proving that the traffic
took the tunnel.

<Callout type="info">
The failure modes on this page come from clearnet-exit integrations. No
equivalent list exists yet for client-to-client work. A visible gap is more use
to you than a guessed one.
</Callout>

## When you are the destination

If you run the service that others reach over Nym, the planning problem inverts.
You never open an outbound connection. Your address is
[only as stable as its gateway](/developers/service-providers#your-address-is-only-as-stable-as-its-gateway).
Every reply you send spends one of the sender's reply blocks, out of a fixed
per-second budget. That is its own page:
[building a Nym service provider](/developers/service-providers).
