# Design: Add Shared Retrieval Index

## Context

Current state, verified against the code on 2026-09-08:

- Storage is two gitignored JSON files in `documentation/docs/public/`, traced into the `/api/mcp` lambda via `outputFileTracingIncludes` (`next.config.js:91-93`) and read with `readFileSync` at cold start (`pages/api/mcp.ts:27-30`, `:57-63`). There is no database of any kind. The one Vercel KV mention in the repo (`ai-assistant-mcp-scratch.md:310`) is a deferred rate-limiting idea, not storage.
- Embeddings are Voyage AI: `voyage-3-large` for docs, `voyage-code-3` for code, both 1024-dim. A content-hash cache under `node_modules/.cache/nym-docs/` avoids re-embedding unchanged chunks across builds.
- Retrieval is a linear cosine scan over all chunks (`lib/retrieval/retrieval.ts:44`), topK default 6, no similarity floor. Roughly 1.6k docs chunks and 7.3k code chunks today.
- The code index covers 20 roots listed in `documentation/indexed-sources.mjs`, all nym-repo paths. Nothing from `nym-vpn-client` is indexed.
- The private boundary is clean: `nym-vpn-client` consumes only the `public/v1` surface of the vpn-api (`nym-vpn-core/crates/nym-vpn-api-client/src/routes.rs`). Everything sensitive (private OpenAPI spec, webhook handlers, payment internals, openspec design docs) lives in the `websites` repo under `www/vpn-api` and `packages/vpn-api-common`.
- The docs site has no access control and publishes every page through four output paths (rendered page, raw `.md` mirror, `llms-full.txt`, `docs-index.json`). Private content cannot be safely mixed into it.
- The retrieval code is already seamed for reuse: `chunkPages` takes `siteUrl`, `collectPages` takes `source`/`expand`/`values`, `stripMdx` is fully injectable. The hardcoded remainder is a handful of module constants (`SITE_URL` in `pages-source.mjs:23`, `GITHUB` in `code-chunker.mjs:13`, cache directory name, `ROOTS`).

## Goals / Non-Goals

**Goals:**

- One index, three producer repos (`nym`, `nym-vpn-client`, `websites`), each owning its shard's freshness from its own CI.
- Private content searchable through an access-protected MCP endpoint, with the public/private boundary enforced by physical store separation, not by application code or a database role.
- Docs deploys decoupled from index size.
- An embedding setup whose privacy properties we control, at minimum for private content.

**Non-Goals:**

- Chat assistant, ANN indexing, quantisation, hand-rolled auth (see proposal Non-Goals).
- Merging or ranking results across public and private shards in one response.

## Decisions

1. **Storage is two separate Postgres + pgvector stores: a public store and a private store.** The corpus (about 9k chunks today, projected 10-30k with the new repos) needs no vector-database features for performance; a sequential cosine scan in SQL is milliseconds at this scale. The public and private split is physical, not a role boundary inside one table: the public store holds only public rows, and the private store holds the private rows beside a re-embedded copy of the public content (decision 2). Self-hosting is required only for the private store, on the transitive-privacy argument that its rows carry private source text a managed host would see; the public store holds only world-readable content, so it may be a managed Postgres. Each store is one table, roughly `chunks(id, repo, source, title, heading, url, text, lang, tokens_est, content_hash, model, dim, embedding vector)`. The private store may keep a descriptive `visibility` tag to tell its public copy from its private rows, but that tag is not an access control. The `embedding` column stays untyped (no fixed dimension) so a store's model and dimension can change; a typed column and index matter only if an ANN index is ever added.

2. **The public/private boundary is physical separation, not a database role.** The public store contains no private row, so no query through the public MCP can return private content: the data is not there to reach, and no application bug or role misconfiguration can widen access to something that is not in the store. The private store lives on separate infrastructure with its own credentials, reachable only by the private MCP; the public server never holds a credential to it. This replaces the earlier row-level-security design. Rather than trusting one store's role configuration to keep two visibilities apart, the sensitive content never shares a store with the public surface. The cost, paid once, is that public content is embedded twice, once into each store; decision 3 covers how the private store gets its copy.

3. **Index production is a push model for the public store, and a private-infrastructure pipeline for the private store.** Each public producer repo (`nym`, `nym-vpn-client`) runs the shared indexer in its own CI and upserts its public shard to the public store, keyed by chunk id with a content hash over the embed text, model, and dimension, so unchanged chunks skip embedding and a model change re-embeds everything (the property the current embed cache keys have). The private store is filled by a pipeline running on the private infrastructure: it runs the same shared indexer over the private `websites` source and over the public repos, embeds all of it with the private model, and upserts the private store. Running this on private infrastructure is what lets it read the private `websites` repo and hold the private store's write credential without handing either to a public repo's CI. This is the pull-based, one-pipeline shape an earlier draft rejected, but the objection then was the private `websites` read token landing inside the public nym docs CI; placing the pipeline on private infrastructure, which is already trusted with private content, removes exactly that objection. So the public content is indexed twice, once per store; that duplication is the price of physical separation, and it is cheap at this corpus size.

4. **The indexer becomes a package, not a rewrite.** Extract `pages-source.mjs`, `chunker.mjs`, `code-chunker.mjs`, `mdx.mjs`, `ts-data.mjs`, `embed.mjs` plus a new upsert module. Parametrise the four hardcoded constants (site URL, GitHub deep-link base, roots list, cache name). The nym-specific projections (`projections.mjs`) stay in the nym repo and are passed in through the existing `expand` seam.

5. **Retrieval stays brute force, and each store is a single embedding space.** Every row in a store is embedded with that store's one model, so a query is embedded once with that model and scanned against the whole store, with no cross-model fusion in the normal path. The public store and the private store are separate spaces and are never queried together in one request: the private MCP answers from the private store alone, which already holds the public content re-embedded in its own space. Scores from the two stores are never compared; if any tool ever combined results across both, it would fuse by rank, never by raw cosine score, since score distributions differ between models.

6. **Runtime query embedding becomes a service concern.** Today each query is embedded by calling Voyage from the lambda. Any self-hosted model path requires an always-on embedding endpoint (text-embeddings-inference or ONNX runtime on CPU; the candidate models answer single queries in tens of milliseconds). This service sits on Nym infra next to Postgres. The private MCP deployment can be co-located there too.

7. **The public MCP server stays on Vercel, now reading the public store.** It remains the `/api/mcp` lambda deployed with the docs site, same URL and deploy story as today; only its data source changes, from bundled files to the public Postgres store over TLS with a read-only credential. Because that store holds only public content, the internet-facing database endpoint carries a bounded risk: a compromise of the pooler or the lambda's credential discloses nothing that is not already public. Vercel functions have no stable egress IPs on standard plans, so the endpoint is internet-reachable through a pgbouncer pooler with a TLS-only listener and scram or client-certificate auth, which also absorbs lambda connection fan-out. If an internet-facing pooler is unacceptable, the fallback is a thin HTTPS query service in front of the public store. Query embedding from the lambda is an HTTPS call to the public store's model provider: Voyage (Option B) or the self-hosted embedding endpoint (Option A).

8. **The private MCP is a self-contained superset server with per-person expiring tokens.** It runs on the private infrastructure next to the private store and the embedder, and answers from the private store alone, which holds the public content beside the private content in one embedding space. So it serves public and private rows through the same tool names with a single query embedding, and depends on neither the public store nor Voyage. It is the single endpoint internal people and external reviewers configure; nobody mounts both servers. Access is a per-person opaque token, stored hashed with an expiry, checked by middleware; external reviewers get tokens scoped to their engagement window, and revocation is a row update, no redeploy. Vercel Deployment Protection was rejected for this endpoint on the transitive privacy argument: it would route private chunk text through Vercel functions, and in this design private text never touches Vercel or the public store. OAuth 2.1 (which MCP clients support) is the upgrade path if per-user identity or token sprawl demands it, not the starting point. If content ever appears that some reviewers must not see, that is a third visibility tier and a third store, added then, not now.

9. **The NymVPN docs site is a later stage of this change, not a separate one.** It reuses the Nextra 2 setup, which is already a self-contained pnpm root. Initial content splits by repo and visibility: the crate and platform READMEs in `nym-vpn-client` are public and seed a public surface; the vpn-api openspec specs and `openapi.json` are not in `nym-vpn-client` at all but in the private `websites` repo (`www/vpn-api`, `packages/vpn-api-common`), so any API reference derived from them is private-visibility content and belongs on the access-protected deployment, not the public site (per the `docs-site-surface` single-visibility rule). Reader access via deployment protection, where the deployment is restricted. The site's private variant, if any, follows the same fail-closed rule: a separate deployment, never filtered pages in a public one. A public site projects from the public store and a private site from the private store, so each is single-visibility because its store is.

10. **The indexer covers every language in a producer's roots, and never drops source silently.** The current code chunker recognises Rust and TypeScript only; `langOf` returns null for anything else, so a Kotlin or Swift file produces no chunk and no error. A dry run over `nym-vpn-client` confirmed the cost: 823 files (the Android and Apple apps, the client's most user-facing code) index to zero. Silent omission is the worst failure for a retrieval index, because a missing answer is indistinguishable from a negative one. So the indexer gains chunking rules for the languages actually present (Kotlin and Swift next), and reports any source-like extension it cannot chunk; absence from the index becomes a recorded decision, not an accident. The chunker stays a line-regex boundary finder, not an AST parser: a new language is a `langOf` entry plus a boundary regex, the same shape as the existing Rust and TypeScript rules.

11. **Language: the indexer and public MCP stay TypeScript; the private MCP is Go.** Three parts, decided apart because the answer differs. The indexer and chunker stay TypeScript: they exist to match the Next.js docs build exactly (MDX stripping, partial inlining, projections, the Nextra `_meta` walk, `github-slugger` anchors), so a second-language port is a permanent drift liability, and this is the code the change extracts rather than rewrites (decision 4). The public MCP stays TypeScript by the platform, since it is a Vercel lambda (decision 7). The private MCP is Go, following its plugin ecosystem: it is more than a query wrapper, it hosts plugins, many of which already exist in or run better in Go, and that outweighs matching the rest of the Rust stack. Choosing a different language for the private server costs no reuse, because a server reads the index from its store rather than importing the extractor (decisions 1-3), so the two share no code regardless of language.

## Open Questions

**Q1: Embedding provider.** Two candidate paths; the choice is the main thing this proposal asks reviewers to weigh in on. Under the two-store design (decisions 1-2) this choice decides only the public store's model: the private store is self-hosted and single-model regardless, so the Third parties and Failure mode rows below describe the public store.

| | Option A: full self-host, one model | Option B: hybrid |
|---|---|---|
| Models | Qwen3-Embedding-0.6B (Apache 2.0) for prose and code | Voyage (`voyage-3-large` / `voyage-code-3`) for public shards; self-hosted Qwen3-0.6B for the private shard |
| Third parties | None | Voyage/MongoDB for public content; nothing private leaves our infra |
| Serving | One embedding service on Nym infra, CPU-viable via ONNX/TEI | Same service, plus the Voyage API dependency and key management |
| Quality | Below the top API models on prose; small gap at this corpus size; must be benchmarked on real queries before cutover | Public shard keeps today's retrieval quality exactly; private shard quality same as Option A |
| Migration | Re-embed everything once (~10-30k chunks, one batch job) | Public shards unchanged; only new private/vpn-client shards embedded |
| Ongoing risk | Retrieval quality regression if the benchmark is skipped | Depends on Voyage's train-by-default opt-out toggle staying set and honoured; two models and two quality profiles to maintain |
| Failure mode | Embedding service down means all search down | Voyage outage takes public search down; private unaffected |

Either way, two actions are independent of the choice: verify the Voyage organisation opt-out toggle is set today, and build a small retrieval benchmark (real queries against the current index as baseline) so any model change is measured, not guessed. If Option A's code retrieval disappoints, `bge-code-v1` (Apache 2.0, above `voyage-code-3` on CoIR) is the quality upgrade at the cost of preferring a GPU.

Load-bearing external claims for reviewers to check: Voyage's train-by-default is in their ToS (voyageai.com/tos, updated 2026-05-27, opt-out prospective only); the `bge-code-v1` CoIR figures are from its model card (huggingface.co/BAAI/bge-code-v1).

**Q2: Rate limiting.** The public endpoint is unauthenticated and every query costs an embedding call. This was already flagged in the code before this change. Postgres does not answer it; a limiter in front of both MCP deployments still needs choosing.

## Risks / Trade-offs

- **New operational surface.** Two Postgres stores (the public one may be managed), an embedding service, the private-infrastructure indexer, and a private MCP deployment are services we now run. Mitigation: they are small, and both stores are stateless in the sense that matters, since the index is fully reproducible from the repos, so backup requirements are modest.
- **Retrieval quality regression on model change (Option A).** Mitigation: the benchmark in Q1 is a gate, not an afterthought; cutover only after it passes.
- **Duplicate indexing of public content.** Public content is embedded twice, once into each store, and the private store re-embeds it with the private model. Mitigation: this is the accepted cost of physical separation, and it is small (about 9k public chunks); the content-hash cache keeps re-runs cheap.
- **Secrets spread.** Public producer CIs gain a write credential to the public store only; they cannot reach the private store, whose write credential lives only on the private-infrastructure pipeline. Mitigation is the separation itself: a leaked public-CI credential writes public content to a store that holds nothing else.
- **The old cross-visibility write hazard is gone.** There is no shared table and no `visibility` column acting as a boundary, so the earlier concern (the `websites` repo writing a `public` row) cannot occur: `websites` content is only ever indexed into the private store, by the private-infrastructure pipeline, and no path carries it to the public store.
- **The vectorless-index failure mode moves.** Today a build without an API key ships a vectorless index; the route half-guards it. In the new design, a failed embed leaves stale-but-valid rows instead, which degrades silently to outdated results. Mitigation: index freshness is exposed (last-successful-run timestamp per shard, in each store) and checked by a scheduled verification job independent of any producer's CI. This check also covers the private store's copy of the public content, which must not lag the public sources; for that copy the check compares against the public sources' content or commit, not only a run timestamp, since a run that succeeded against an older revision would pass a timestamp check while serving stale text. A stale copy degrades the private server's answers on public topics but never crosses a visibility boundary.

## Migration Plan

1. Doc fixes and small guards land first (independent of everything else).
2. Indexer package extracted; the public store stood up (may be managed); nym CI dual-writes: files as today, plus the public store.
3. Benchmark built; embedding decision (Q1) made against it. Q1 now decides only the public store's model; the private store is self-hosted and single-model by decision 8.
4. Public MCP route reads the public store behind a flag; verified with `check-mcp-server.sh`; flag flipped; file generation and tracing removed.
5. `nym-vpn-client` CI wired to the public store. Private infrastructure stood up: the self-hosted private store, the embedding service, and the private-infrastructure indexer that fills it from the public repos and the `websites` source with the private model; private MCP deployment on top.
6. NymVPN docs site stage begins.
