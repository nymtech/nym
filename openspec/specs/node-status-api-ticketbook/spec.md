# node-status-api-ticketbook Specification

## Purpose

Defines the ecash ticketbook subsystem that keeps a buffer of pre-issued ticketbooks used to pay for gateway test runs. It deposits on the `nyxd` chain, obtains threshold-signed ticketbooks from the ecash signing quorum, persists them, and attaches ticket materials to assigned test runs.

## Requirements

### Requirement: The ticketbook manager SHALL maintain a buffer per ticket type on a timed loop

The manager MUST run on an interval (default 60s), prioritizing shutdown in a `biased` select. Each tick it MUST ensure credentials are issuable, check that the ecash quorum is available, and for each buffered ticket type refill the buffer: if available tickets ≥ the buffer size it is a no-op; otherwise it MUST compute the number of ticketbooks needed (ceil division), deposit on chain in chunks bounded by `max_concurrent_deposits`, obtain aggregated wallets from the signing quorum, and persist the issued ticketbooks.

#### Scenario: Buffer above threshold is a no-op
- **GIVEN** available tickets of a type ≥ the configured buffer size
- **WHEN** the manager ticks
- **THEN** no deposits are made for that type

#### Scenario: Refill below threshold
- **GIVEN** available tickets of a type below the buffer size and an available quorum
- **WHEN** the manager ticks
- **THEN** it deposits the needed ticketbooks on chain (in bounded chunks) and persists the threshold-signed ticketbooks

### Requirement: Refill SHALL respect shutdown between chunks and persist a recovery row on aggregation failure

Deposits MUST be made in chunks bounded by `max_concurrent_deposits`, checking for shutdown *between* chunks so that an in-flight chain operation is not abandoned mid-deposit. If wallet aggregation from the quorum fails, the manager MUST persist a pending/recovery row rather than losing the deposit.

#### Scenario: Shutdown honored between chunks
- **GIVEN** a multi-chunk refill in progress
- **WHEN** shutdown is signalled between chunks
- **THEN** the current in-flight chain operation completes and no new chunk is started

#### Scenario: Aggregation failure persisted for recovery
- **GIVEN** a completed on-chain deposit whose quorum wallet aggregation fails
- **WHEN** the failure occurs
- **THEN** a pending/recovery row is persisted so the ticketbook can be recovered

### Requirement: The manager SHALL warm a startup cache of ecash state

At startup `build_initial_cache` MUST warm the epoch, deposit amount, master verification keys, threshold, and signatures so subsequent refills and material assignment do not re-fetch them each cycle.

#### Scenario: Startup cache warmed
- **WHEN** the ticketbook manager state is built at startup
- **THEN** epoch, deposit amount, keys, threshold, and signatures are pre-loaded

### Requirement: Ticket materials SHALL be atomically assigned to a test run

`has_enough_ticketbooks` MUST require the (duplicate-aware) buffered count per type before assignment is allowed. `attempt_assign_ticket_materials(testrun_id)` MUST pull one next-ticket per buffered type, atomically incrementing the spent count and linking the ticket to the test run, and collect the per-epoch verification key plus coin-index and expiration-date signatures into an `AttachedTicketMaterials`. Reading the next unspent ticketbook MUST be an atomic update (`UPDATE ... used_tickets+1 WHERE id = (SELECT ... FOR UPDATE)`), and the retrieved usable index MUST be `spent - 1` (erroring when spent is 0).

#### Scenario: Assignment gated by buffer sufficiency
- **GIVEN** insufficient ticketbooks of one buffered type
- **WHEN** a test-run assignment checks `has_enough_ticketbooks`
- **THEN** assignment is refused until the buffer is replenished

#### Scenario: Atomic next-ticket claim
- **GIVEN** concurrent assignments
- **WHEN** each pulls the next unspent ticketbook
- **THEN** the used-ticket counter is incremented atomically under `FOR UPDATE`, giving each caller a distinct usable index

## Technical Notes

- **Implementation**: `ticketbook_manager/mod.rs` (`TicketbookManager::run`, `check_ticketbooks_buffer`, `maybe_refill_ticketbook`), `ticketbook_manager/state.rs` (`TicketbookManagerState`, `build_initial_cache`, `has_enough_ticketbooks`, `attempt_assign_ticket_materials`), `storage/auxiliary_models.rs` (`RetrievedTicketbook`, `StoredIssuedTicketbook` with Zeroize), `db/queries/ecash_data.rs`.
- **Config**: `--tickets-buffer-size` (default 50), `--max-concurrent-deposits` (5), `--tickets-buffer-check-interval` (1m), `--quorum-check-interval` (5m), `--buffered-ticket-types` (default includes `V1WireguardEntry` twice), `--mnemonic`, `--ecash-client-identifier-bs58`.
- **External services**: `nyxd` chain (deposits) and the ecash signing quorum (threshold signing) via `nym-credential-proxy-lib`; a `QuorumStateChecker` tracks quorum availability.
- **Related specs**: consumed by [[node-status-api-testruns]]; persisted via [[node-status-api-persistence]]; the resulting `AttachedTicketMaterials` are imported by [[gateway-probe]] through the [[node-status-agent]].
