## Purpose

This overview describes a three-part subsystem that measures and reports the health of Nym network nodes - primarily the dVPN-facing capabilities of gateways (WireGuard, Lewes Protocol, SOCKS5, exit-policy ports, geolocation), and secondarily mixnet routing and mixing performance. The **node status API** persists a snapshot of the network and serves it over HTTP, while also orchestrating gateway "test runs". External **agents** poll the API for assigned test runs, execute network diagnostics against a target gateway using the **gateway probe** library, and submit signed results back. Together they produce the connectivity/performance data that powers dVPN gateway directories and network dashboards.

## Requirements

### Requirement: The subsystem SHALL comprise three cooperating components with a defined data flow

The subsystem MUST consist of three deployable components plus one shared client library:

- **`nym-gateway-probe`** — a Unix-only CLI/library that connects to a Nym gateway and exercises mixnet, WireGuard, Lewes Protocol (LP), SOCKS5, and TCP-port-reachability paths, emitting a structured `ProbeResult` / `PortCheckResult`.
- **`nym-node-status-api`** — a long-running service that scrapes the directory (`nym-api`) and chain (`nyxd`), persists network state to PostgreSQL, serves a read HTTP API, and queues/assigns gateway test runs.
- **`nym-node-status-agent`** — a CLI worker that requests a test run from the API, runs the probe in-process, captures its logs, and submits signed results back.
- **`nym-node-status-client`** — the shared HTTP client library defining the signed request/response contract between agent and API.

The data flow MUST be: API enqueues test runs for bonded gateways → agent requests an assignment (authenticated by ed25519 signature) → API atomically claims the oldest queued run and attaches ecash ticket materials → agent runs the probe and submits results → API marks the run complete and updates the gateway's stored probe result and score.

#### Scenario: End-to-end test run lifecycle
- **GIVEN** the node status API has queued a probe test run for a bonded gateway and holds enough ecash ticketbooks
- **WHEN** an authorized agent requests a test run, runs the gateway probe against the assigned gateway, and submits the result
- **THEN** the API stores the probe result and updated score against that gateway and marks the test run complete, and the data becomes visible on the public read endpoints

#### Scenario: Components are independently invokable
- **WHEN** the gateway probe is invoked directly by an operator (not via an agent)
- **THEN** it performs the same diagnostics and prints a JSON result to stdout without requiring the node status API
