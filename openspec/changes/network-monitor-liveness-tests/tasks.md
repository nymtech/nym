## 1. Provisional defaults and the one compatibility check

- [x] 1.1 Adopt the provisional liveness profile defaults (50 packets per target, a PER-TARGET rate of 50 packets/second, a 5 second straggler wait, wave sizes of 100 mixnode and 50 gateway targets) and make every one of them CLI- and env-overridable, so an agent host that cannot sustain a full wave is a configuration change rather than a code change. The rate sits well below the stress profile's 1000/s so that no target is under load, and puts a target's send window at about one second, since a probe asking whether a node forwards at all has no reason to hold one open longer. A full wave's aggregate is consequently 5000/s (~15 Mbps at `AckPacket` sizing) for that second, above a stress run's rate but a sixth of its volume; the aggregate is deliberately left to scale with the orchestrator's wave size rather than being capped agent-side

A 30 second per-target timeout fits inside the orchestrator's existing 1 minute lease, which the profile already satisfies without change: ~1 second of sending plus the straggler wait plus TCP and Noise setup, all concurrent across the wave, so the deadline is dominated by setup rather than by sending

## 8. Agent: liveness profile and wave concurrency

- [x] 8.1 Add the liveness probe profile alongside the stress profile in the tester config, carrying the per-target rate directly. The packet count is the primary knob and the send window derives from it (`count / rate`), inverting the stress profile's `rate x duration` shape, so `expected_packets()` cannot be shared between the two. The sending batch size is DERIVED from the packet count as a fixed number of dispatches across the window rather than inherited or configured: the interval is `batch / rate`, so the stress batch of 50 would collapse the profile's 50-packet probe into a single burst, and pinning a batch size instead of the dispatch count would break again the moment the provisional count or rate moves. Ack sizing needs no knob: both packet-building paths already use `PacketSize::AckPacket`, so liveness inherits it
- [x] 8.2 Bind ONE shared ingress listener per invocation, resolving each inbound connection to its target through one canonicalised source-keyed table and giving the responder a `NoiseNetworkView` scoped to just that connection's source. A wave-spanning view was specified here originally and turned out to be redundant: `upgrade_noise_responder` consults the view only via `supports_noise(source)` as a membership gate and `perform_responder_handshake` then reads only `config.local_key`, so the initiator's key plays no part on this side and a wave-wide view would duplicate the known-source set. A target's noise key is genuinely needed only by the INITIATOR (`get_noise_key`), which is its own egress connection. The listener must also stop handling one connection at a time, and its single `last_noise_handshake_duration` becomes per-source, since one field cannot attribute N targets. The ingress handshake stays MANDATORY per target rather than becoming optional: the harvest is only reached
  after that target's connectivity probe succeeded, and a returned packet means the node already connected back and handshook as responder, so the existing hard error is retained as a check on the new per-source plumbing. Small gain from the change: the source is known at accept time, before the handshake, so a FAILED ingress handshake becomes attributable to a target instead of an anonymous log line
- [x] 8.3 Make the known-source set the union of every target's announced addresses, canonicalised. Two targets in one wave announcing the same ip are deliberately NOT handled: the later one wins the ip-keyed slot, the other then presents an unexpected static key on its return connection, fails the responder handshake, receives nothing and scores zero while its twin scores normally. That is the intended penalty for a misconfigured pair, it is self-diagnosing from the results (a node permanently at zero beside a healthy twin), and both are still reached correctly on egress, which carries the port
- [x] 8.4 Attribute returned packets to a target by the source address of the connection they arrive on, and accumulate per-target results. Attribution is structural rather than per-packet: a connection resolves to its target once, before the handshake, and its handler then delivers to that target's `TargetInbox` alone. Accumulation is per TARGET rather than per connection because duplicates and counts are properties of a target's whole result set - a node may reply over more than one connection, and no single connection can tell whether an id has been seen already
- [x] 8.5 Execute a wave as one concurrent batch with a hard per-target deadline, so the wave's duration is bounded by the slowest single target. `NodeStressTester::run_stress_test` becomes `NodeProbe::run(profile)` now that it runs both kinds; the crate-local `TestRunResult` keeps its name
- [x] 8.6 Submit each target's result as soon as that target finishes rather than at the end of the wave, and never let one target's outcome abort the wave. A node-level failure (unreachable target, nothing returned) IS the measurement and MUST be submitted even when zeroed, because submission is what writes that pairing's `last_tested_at` and so defers the node a full staleness interval; hand-out advances only the address rotation pointer. A critical agent-side failure submits nothing and lets the lease expire instead, so the node keeps its turn rather than being scored zero for our bug, at the accepted cost that a persistently broken agent re-leases the same nodes every lease period, visible in the agent's logs only
- [x] 8.7 Unit-test attribution across a wave (several targets returning interleaved packets), and that one target timing out does not extend the others. ATTRIBUTION is covered at the connection handler's read level: `handle_stream` and `report_handshake` are generic over the stream, so tests instantiate them with a plain iterator of packets and assert per-target delivery, decrypting each with that target's OWN reusable header so a misdelivery fails to decrypt rather than merely landing in a bucket whose count happens to match. Five tests: concurrent connections delivering to their own targets, a connection from a target's other announced address, an unknown source dropped, a completed handshake ahead of its packets, a failed handshake reaching only its own target. The recorded trade is that they cover neither the socket accept nor the Noise upgrade.

      The TIMING half was examined and deliberately NOT unit-tested. `MixnetWave::run` binds a real listener and each probe TCP-connects and handshakes as initiator, so a target has to be a real endpoint; worse, a fake target that accepts and goes silent fails the Noise handshake and exits down the egress-failure path instead of reaching the deadline, so provoking a timeout needs a fake nym-node running `upgrade_noise_responder` with the key the probe expects and then going quiet. `tokio::time::pause` cannot be used alongside real sockets (auto-advance fires while a connect is pending), so the test would be real-time and timing-sensitive - the same flake this task's attribution half was seamed to avoid. What it would prove is `join_all` polling concurrently and `timeout` expiring, both library contracts; the agent's own logic is two lines. Covered instead by 12.4 end to end, plus two cheap guards over the pure functions that could regress silently: `each_kind_resolves_to_its_own_profile` (swapped arms would apply the wrong profile to both kinds) and `only_a_liveness_probe_carries_a_per_target_deadline` (losing the deadline would remove the bound entirely). Both were mutation-checked

## 9. Agent: gateway client session and the two-phase probe

- [x] 9.1 Use the derived ed25519 client identity from 2.8 for the session, with no new on-disk key and no per-test regeneration (the identity must match what was announced). Held once on the agent and cloned into every probe of a wave, since a wave registers one session per target concurrently under the one identity. That is only safe because a wave's targets are DISTINCT gateways: a gateway keys its active sessions by client address, so a wave listing the same gateway twice would have its second session dropped on `insert_remote` and score that target as dead. Checked when the wave is built rather than trusted, because a confusing score is a poor way to learn of an assignment bug
- [x] 9.2 Establish the client session at `ws://<assigned-ip>:<clients_ws_port>`, constructed directly from the assignment, ignoring announced hostnames and wss entries and not reusing `ws_entry_address`. "No TLS" is structural rather than conventional: the session's transport type is `WebSocketStream<TcpStream>` rather than `MaybeTlsStream`, so there is no variant a certificate could arrive on and no code path a resolver could enter. Establishment ALWAYS registers and never authenticates, since an unmetered session persists no shared-key row for an authenticate to look up; the cost is one handshake per run, which suits a process that exits after a single assignment. The session's protocol version is the one the handshake SETTLED on rather than the one proposed, because the handshake may downgrade and it is the settled version that selects the forward-request variant
- [x] 9.3 Implement the ingress phase: forward a sphinx packet through the session whose next hop is the agent's own mixnet address, and count arrivals at the shared listener. A one-hop sphinx route naming the agent, wrapped in an envelope whose next hop is the agent's own return address. Needed nothing added to the wave's routing: the packets reach the shared listener over the gateway's own outbound mixnet connection and are attributed by the gateway's source address, which `WaveIngress` already resolves. A one-hop route also makes the outbound and returning forms of a packet IDENTICAL, since no earlier hop peels a layer off it, so the reusable-header recovery works unchanged and group 8's `create_returned_packet` distinction does not arise here
- [x] 9.4 Implement the egress phase: send final-hop packets to the gateway's mixnet listener addressed to the agent's own client session, and count arrivals on that session. Ack-sized on purpose and not merely to stay small: at that size `split_into_ack_and_message` returns the payload whole rather than trying to recover a SURB-Ack from the front of it, so the content reaches the session verbatim. No sphinx recovery on receipt either, because the gateway was the packet's final hop and unwrapped the payload before pushing it - `PayloadRecovery` is not involved on this leg and only the content is parsed
- [x] 9.5 Hold the session open across both phases and their drain windows, and use one address family for both legs with the sphinx return hop matching it. The session is closed in the run's `finish` and nowhere earlier, so it outlives both phases and both drain windows; closing it per phase would turn a delivered packet into a dropped one. One family holds by CONSTRUCTION rather than by check: the session address takes its ip from the mixnet target, and the return hop comes from `return_address_for`, which follows the family it is given. Both legs also ask for a ZERO sphinx delay, unlike the mixnode probe which subtracts one delay from every round trip: no delay is ever applied here, since the ingest leg's gateway forwards the packet verbatim without any sphinx processing and on the delivery leg the gateway is the FINAL hop, which carries no delay to apply. Asking for one and not subtracting it, or subtracting one never applied, would bias every latency figure by its length
- [x] 9.6 Produce two measurements with a fixed two-measurement denominator: a phase that produced nothing scores zero, a phase-1 failure does not abort the run, and a session that cannot be established yields two zero measurements. The denominator is STRUCTURAL rather than remembered: the result is seeded with a zeroed measurement per expected interface and the measurement set has no `insert`, so a phase that never ran keeps its seed and an interface the role should not produce is unrepresentable. A phase failure is recorded against that phase and execution proceeds to the next. Failing to establish the session sets the RUN-level error and returns the seeded pair, which is the only outcome that makes a node unreachable rather than merely unmeasured. Per-interface error strings are LOCAL only, since `InterfaceMeasurement` carries no error field; folding them into the run-level error was rejected because that field drives `was_reachable`, so a gateway with a broken ingest and a working
  delivery would be reported unreachable while scoring 0.5. Carrying them on the wire is a schema change and is left out of this group
- [x] 9.7 Unit-test the scoring rules of 9.6, including that a healthy-ingress / dead-egress run scores 0.5 rather than 1.0. The 0.5 assertion is discharged by group 10's `a_missing_phase_scores_zero_rather_than_shrinking_the_denominator`, since the average and its denominator are computed in the orchestrator rather than by the agent; duplicating it here would test the agent against arithmetic it does not perform. What IS covered agent-side: the seeded set at the measurement level (both interfaces submitted, one measured interface not displacing its unmeasured sibling, an unexpected interface dropped), and the session-failure rule by a probe aimed at a refusing port, which also pins that such a run returns a submittable result rather than an error - an error would leave the target unreported and its lease held instead of scored. NOT covered, and recorded rather than written: that a phase-1 failure does not abort the run. It needs a gateway that completes the registration handshake and
  then refuses forwards, and the phases take `&mut self` on a struct holding a live session, so testing it would mean widening the session into a trait for one test

## 10. Orchestrator: per-kind submission

- [x] 10.1 Split the result submitter into one stream per kind, each reading and advancing its own watermark and posting to its own endpoint. The sweep iterates `TestKind` itself rather than calling two hand-written stream functions, so a future kind cannot be added without a stream to submit it, and a stream whose POST fails is logged and skipped rather than aborting the sweep
- [x] 10.2 Convert a liveness run into its submission shape: the average over the kind's fixed measurement set with a missing measurement counted as zero. An interface that saw duplicates counts as zero too, matching the stress path, because a node replaying one packet nine times counts ten received against ten sent and the clamp on the ratio caps that at a perfect score rather than preventing it. The average is taken over the expected set rather than over the measurements that arrived, so an absent interface counts as an explicit zero and one the role should not have produced is ignored. AMENDED during group 11: the submission carries the averaged score ALONE and no per-interface breakdown, so its shape is identical for a mixnode and a gateway. Because the expected-set denominator is what makes a gateway with a dead phase score 0.5 rather than 1.0, and neither the role nor the interfaces reach the wire, the averaging MUST stay on this side

Mounted at `/v3/nym-nodes/liveness-testing/batch-submit`, matching the constants the validator-client already posts to; `utoipauto` scans `./nym-api/src`, so the `#[utoipa::path]` annotation needs no manual registration in `ApiDoc`. The five ordered checks are DUPLICATED from the stress handler rather than abstracted over the two body types: Decision 9 requires only that the two paths not share replay STATE, the sequence is security-relevant and is easier to audit when its order is readable in one place, and generifying it would need a trait over `SignedMessage<T>` for `signer` / `timestamp` / `is_stale` that has exactly two implementors. The authorised-orchestrator check deliberately DOES share the stress path's `NetworkMonitorsCache`, since one contract lists the orchestrators and authorisation is not per-kind;
  liveness therefore gets no `known-monitors` route of its own. Step 6 returns `501` until 11.3 adds the table, which is deliberate rather than a `200` with zero counts: the orchestrator advances a stream's watermark only after a successful POST, so an error makes it re-send those rows once storage exists whereas a bare success would silently drop the batch. NOT covered here: an endpoint-level test, which needs the `axum_test` harness and lands in 11.7. Note also that nothing in this crate tests `ApiDoc::openapi()` generation at all, which is pre-existing and not introduced by this route. The staleness window is now a shared `SUBMISSION_STALENESS_WINDOW` const read by BOTH handlers, replacing two independent `Duration::from_secs(30)` literals that could have drifted apart silently, and the pre-existing "make the timeout configurable" TODO was dropped rather than duplicated: its stated blocker (no easy way to propagate config values) is long stale, since `AppState` is built with
  `config` in scope and four sibling fields already take config values, so the TODO was recording a non-problem. It is deliberately NOT made configurable - no one has asked to tune it and the delta spec fixes 30 seconds as normative - and the const is the single place that becomes a config read if that ever changes
- [x] 11.2 Scope the per-signer replay high-water mark per endpoint so the stress and liveness streams cannot invalidate each other. `LastNMSubmissions` now holds TWO named maps, `stress` and `liveness`, with four accessors named for their stream, so a handler states which stream it speaks for and cannot silently read the other's mark. Both fields are private (the single map was `pub(crate)`), which is what stops a future caller reaching past the accessors and losing the scoping. Two alternatives were rejected as more complex for no gain: keying one map on `(stream, signer)`, which needs a discriminator enum and an unreadable map type; and splitting into two `AppState` fields, which spreads one concept across the state struct and grows it per future kind. The test uses ONE DECOY PER COMPONENT of what makes a mark distinct - the other stream for the same signer, and the same stream for another signer - because a lookup ignoring either would otherwise still pass
- [x] 11.3 Accept gateway-capable nodes on the liveness endpoint and store each result's single averaged score, deduplicating on `(node_id, test_timestamp, submitter_pubkey)`. AMENDED twice from "store each result with its per-interface breakdown, deduplicating on `(testrun_id, submitter_pubkey)`". The breakdown no longer reaches nym-api at all (see 10.2 and Decision 11), so there is no child table on this side. And the original dedupe key is the one migration `20260806120000_stress_testing_result_identity` was written to REMOVE from the stress table: `testrun_id` is an orchestrator-local autoincrement, so a wiped orchestrator database restarts it at 1 and every resubmitted id collides with a stored row and is dropped silently behind a `200` until the counter passes its old high-water mark, while a restore-from-backup is worse still because an id then means a different measurement on each side. Identity is the measurement, exactly as on the stress table; keep `testrun_id` as a non-key
  column so a row stays traceable to the submitter, and give the table its own AUTOINCREMENT id rather than a rowid alias so retention deletes cannot recycle handles. AS BUILT: migration `20260903120000_liveness_testing` creates `nym_node_liveness_result` as a SEPARATE table rather than adding a kind column to the stress one - the kinds are separate streams end to end (own endpoint, own replay mark, own watermark, own aggregation, own weight), and a shared table would need a discriminator every read must remember to filter on, silently blending a zero-weighted population into a scored one when forgotten. Gateway acceptance turned out to need NO code: a liveness result carries no role at all, so there is nothing to relax, and the only per-entry validation left is the `[0.0, 1.0]` range check. Inserted through `QueryBuilder` like the stress path, which means it is NOT schema-checked at compile time, so the three storage tests are what actually exercise the migration - `init_in_memory`
  runs `sqlx::migrate!` identically to the file-backed constructor. They use one decoy per key component, plus a dedicated regression guard that a REUSED testrun id neither duplicates a stored measurement nor blocks a fresh one, which is the whole point of the amended key. No `.sqlx` regeneration is needed, here or later: nym-api tracks 85 offline files but nothing sets `SQLX_OFFLINE` for it, so its macros always compile against the database `build.rs` builds from `./migrations`; anyone who does set that flag must run `cargo sqlx prepare` after adding a macro
- [x] 11.4 Aggregate liveness results (average performance plus a reachability flag over a window) into a liveness score. `get_average_node_liveness_score` mirrors the stress query: `AVG(result)` with `MAX(was_reachable)` so a window is reachable if ANY sample reached the node, and `GROUP BY node_id` so an empty selection yields NO ROW rather than one all-NULL row - that is what lets `None` mean "no sample" and `Some(0.0, false)` mean "probed and delivered nothing", a distinction the availability gate in 11.5 depends on. The average is over whole RUNS, each already averaged over its own interfaces by the orchestrator, so a dual-role node folds its mixnode and gateway runs into one figure as the delta spec requires. New `LivenessScore { score, was_reachable }` in nym-api-requests is a distinct type from `StressTestingScore` rather than a reuse, because the two are separately weighted and liveness ships at zero - a consumer that confused them would silently weight an inert score.
  `liveness_data_period` is a separate config knob from `stress_testing_data_period` (default 24h, same value, different cadences) added to both the config struct and the template; `PerformanceProviderDebug` carries `#[serde(default)]` at container level, so existing config files without it still parse. The three gating flags stay with 11.5, which is also what consumes the four methods currently warning as dead code. TRAP HIT AND FIXED: `nym-api/build.rs` had no `cargo:rerun-if-changed`, so adding a migration did not re-run it and the `query_as!` macro compiled against a scratch database that predated the new table - surfacing as "no such table: nym_node_liveness_result" for a migration plainly present on disk. 11.3 never noticed because it adds no macro. The script now declares `migrations` and `build.rs` as its inputs, which also opts it out of cargo's "any package file changed" heuristic and is why `build.rs` itself has to be listed
- [x] 11.5 Add the liveness performance component to the provider behind its own `use_*`, `minimum_available_*` and `*_score_weight` flags, with the weight defaulting to ZERO. The formula moved from five positional params to a named `PerformanceComponents { routing, config, stress: Option<WeightedComponent>, liveness: Option<WeightedComponent> }`: a third component would have made it seven positional bools and floats, and `Option` rather than a zero weight keeps "not in scope for this test" distinct from "measured and scored zero", which is what stops an out-of-scope node taking a weighted zero for a test it never faced. It is a weighted MEAN in which each applied component takes its weight and routing x config takes the remainder, so with nothing applied it is exactly routing x config - that identity is what makes a zero-weighted liveness component provably inert, and it is asserted directly rather than assumed, with a converse test so it cannot pass merely because the component is never wired in. Config validation rejects `stress_testing_score_weight + liveness_score_weight > 1.0` unconditionally, because oversubscribing the budget drives the remainder NEGATIVE and would penalise a node for routing well; enforced at startup rather than clamped at use, so a misconfiguration fails loudly. `liveness_eligible` is wider than `stress_test_eligible` - `declared_role.mixnode || declared_role.entry`, mirroring the orchestrator's `NodeType::from_roles` treating only `(false, false)` as `Unknown`, with `entry` confirmed as that same `gateway_enabled` flag at `type_translation.rs:441` - so each component takes its availability ratio over its OWN eligible population; one shared denominator would let the network's mixnode:gateway composition decide whether either dataset is trusted at all. The score is FETCHED and ANNOTATED unconditionally, NOT gated on `use_liveness_data`, which is what keeps it queryable and keeps 11.6's divergence gauge working while the weight is zero; the flags only control the fold. `use_liveness_data` defaults false, matching stress, and that flag is what makes liveness inert. AMENDED from "weight defaulting to ZERO": a zero default weight is a SECOND gate on the same property, whose only observable effect is a state reading as enabled while changing nothing, indistinguishable from a bug. `liveness_score_weight` therefore defaults to 0.2, matching stress, so enabling is one change rather than two; the tradeoff, recorded in the config template where an operator reads it, is that the flip takes effect immediately and so wants the divergence surface consulted BEFORE it. `liveness_score_weight` is still surfaced in the template even though `stress_testing_score_weight` is not, so the shared weight budget is visible next to the flag that spends it. SCORING RESTRUCTURED after this task was first ticked, on the user's call, because adding a third component exposed a defect in the formula rather than just crowding it. The old shape gave each enabled component its weight and let `routing x config` absorb the remainder, so a component ESCAPED the config gate - with stress at 0.3, three tenths of a node's performance ignored its config score, letting an out-of-date or unfunded node partially buy that back by stress-testing well. Since routing, stress and liveness all measure the same thing from different sources, they are now proportions of ONE delivery figure multiplied by the config score: `(sum(w_i * s_i) / sum(w_i)) * config`. The per-node delta from the old form is exactly `stress_weight * stress_score * (1 - config_score)`, so nodes at config 1.0 are unaffected and the rest lose a shield they should not have had; `chain_interactions_penalty` widens that population but does not change the structure, sitting inside the config score already. Renormalising over the APPLIED set is load-bearing twice over: stress covers mixnodes only, so a gateway would otherwise be docked its share for a test it cannot take, and a threshold tripping mid-flight would otherwise deflate the whole network for an orchestrator outage. Consequence recorded rather than hidden: effective weights differ by role, so a declared weight is a share of whatever applies. An empty applied set yields NO score and leaves the previous annotation standing, since zero slashes a node for our gap and anything else rewards it for nothing. Weights moved into a pooled `[performance_provider.scoring]` section of `ScoreProperty { enabled, weight }` per property (`legacy_v1_routing`, `stress_testing`, `liveness`), which turns validation into a fold over a named set: enabled weights sum to 1.0, at least one enabled with non-zero weight, at least one of routing or liveness (stress alone leaves gateways unscoreable), and none enabled alongside contract data. The sum check uses a tolerance rather than `!= 1.0` because binary floats make the exact test reject clean configs - 0.7 + 0.2 + 0.1 is 0.9999999999999999 while 0.34/0.33/0.33 is exactly 1.0 - and it is order-dependent; 1e-9 still rejects 0.33 three times. The two RELEASED keys `use_stress_testing_data` and `stress_testing_score_weight` are `#[deprecated]` `Option`s resolved by `PerformanceProvider::apply_deprecated_fields`, a FIXUP that runs before the pure `validate` rather than inside it, warns per key, and also derives routing's weight as `1.0 - stress` so a config predating the section still boots instead of failing the sum rule on upgrade. `#[allow(deprecated)]` sits on the struct and on the two legitimate write/read sites so accidental use elsewhere still warns. The liveness and routing pairs needed no migration path, being unreleased. Also added a template render test, since the template is only exercised at `init` and a mistyped variable would otherwise first appear as a panic in front of an operator. REFRESH BUG FOUND AND FIXED while here: `refresh` fetches every component unconditionally with `?`, and `ContractPerformanceProvider` returned `Err` for stress (pre-existing) and would have for liveness, so selecting the contract provider aborted the refresh before it wrote a single annotation - and since the caller discards that error, the only symptom was a node status cache that silently stopped updating. Both batch methods now report ABSENCE via a new `empty()`, matching what `get_batch_node_routing_scores` already did, which is safe because config validation forbids enabling either component alongside contract data. TS BINDINGS NOT REGENERATED: `LivenessScore` is registered in `tools/ts-rs-cli` so `make generate-typescript` emits it, which is REQUIRED or `DetailedNodePerformanceV2`'s generated import dangles, but the checked-in bindings are prettier-formatted by the `pnpm types:lint:fix` half of that same make target and `lerna` is not installed here, so running only the Rust half produced unformatted output across 13 files that the project's own tooling would reformat. The bindings are also already drifted repo-wide (`ConfigScore` was renamed to `ConfigScoreV1`/`ConfigScoreV2` in Rust and never regenerated), so regenerating them is a separate chore rather than this change's to carry
- [x] 11.6 Add the divergence surface comparing a node's aggregated liveness score against the v1 routing score, per node, carrying both scores, their difference, the reachability flag and the declared role. AMENDED: the wss bucketing in the original wording (and in Decision 12) was REJECTED as unjustified complexity requiring more retrieval than the question needs. It is inert for mixnodes, which announce no entry interface and are most of the population, and second-order to the confound that dominates during rollout - whether a node yet carries the group 6 and 7 behaviour at all. The two dominant confounds also have OPPOSITE signs (broken TLS puts liveness above routing, an un-upgraded node puts it below), so they separate in aggregate without a bucket. Declared role is the one dimension kept, and only because it costs nothing: `declared_role.mixnode` / `.entry` come off the described-nodes cache that `AppState` already holds and 11.5 already reads. Served at `GET /v3/unstable/nym-nodes/liveness-divergence` under the UNSTABLE tree, with a module-level notice that it is temporary and to be DELETED once liveness is either weighted or dropped - it makes no compatibility promise and nothing durable may be built on it. `OutputParamsV2` rather than `OutputParams`, so it offers json and yaml but NOT bincode: bincode is the format carrying the field-ordering compatibility hazard, which a route slated for deletion has no business exposing. It is a pure projection of caches nym-api already maintains - annotations for both scores, described for the role - so it runs no storage query and needs no new state. Every liveness-eligible node is listed INCLUDING those with no sample (zero score, `was_reachable` false), because coverage is half of what the surface is read for: deciding the weight needs how much of the fleet has been measured as well as how the measured part compares. Nodes declaring neither role are OMITTED rather than reported as diverging by zero, matching `NodeType::Unknown` never being assigned a test. Two limits are recorded rather than papered over: a dual-role node's score already averages both its probes, so its role labels the node and not the measurement; and the surface cannot say which half of a gateway is dead, that being a lookup against the orchestrator's own read surface
