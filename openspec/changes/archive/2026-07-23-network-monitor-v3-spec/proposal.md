## Why

The network-monitor "v3" subsystem is Nym's active mixnode stress-tester: a fleet of short-lived agents drives high-rate sphinx traffic through individual mixnodes (looped back to the agent), an orchestrator collects the per-node results and submits them to nym-api, and nym-api folds them into node-performance scoring and, downstream, rewarding. It is a chain-authorised, off-chain distributed system spanning four subsystems of this repository (the `contracts/network-monitors` CosmWasm contract, the `nym-network-monitor-v3/` orchestrator and agent crates, the nym-api ingest path, and the nym-node side that reacts to on-chain agent authorisations), and it exists only as Rust source plus scattered comments.

Several behaviours are load-bearing but non-obvious from any single file, and get re-derived from scratch during triage:

- **Authorisation is chain-backed and node-local, not orchestrator-asserted.** The contract is a three-tier registry (admin authorises orchestrators; orchestrators authorise agents). Crucially, each nym-node independently learns the authorised-agent set from the contract - a one-time load at startup plus a REAL-TIME nyxd websocket event subscription - and folds it into the routing filter, the Noise handshake map, and, most importantly, the sphinx replay/bloomfilter BYPASS. A node drops a replayed packet UNLESS its source IP is that of an authorised agent. So an agent's high-rate replayed probe only works after it is authorised on-chain AND the node has ingested the event, and the whole trust model turns on this node-side propagation.
- **The agent is a one-shot job, not a daemon.** Each invocation announces, requests one assignment, tests one node, submits, and exits; fleet scale is many short-lived runs. Authentication to the orchestrator is a static bearer token with NO request signing; the agent's only cryptographic identity is its on-chain socket + noise key.
- **A stress test is a two-hop self-loop, and the score deliberately penalises back-pressure.** Packets traverse `[tested_node, this_agent]` at a fixed rate for a fixed window; on success the reported `packets_sent` is overwritten with the EXPECTED count (not the actual), so a node that throttled the agent via TCP back-pressure is scored as if fully loaded. The `reuse_header` default replays one sphinx header specifically to exercise the node's monitor-replay bypass.
- **Submission to nym-api is signed, monotonic, and at-least-once.** The orchestrator signs each batch with its ed25519 identity key; nym-api verifies staleness (30s), contract membership, strict timestamp monotonicity (a per-signer high-water mark), and the signature, then deduplicates at the database by `(testrun_id, submitter_pubkey)`.
- **It tests mixnodes only today.** The orchestrator, the created test type, and the nym-api ingest all restrict to mixnodes; a gateway test type exists in the data model but is unwired.

Capturing the spec now - while the behaviour and rationale are fresh - is materially cheaper than reconstructing it from source later, gives the on-chain authorisation and replay-bypass model a normative reference, and provides the baseline against which the known future work (single-hop liveness replacing the v1 monitor, and taking over node-status-api gateway probing) will be specified.

This subsystem is distinct from two others that share the "network monitor" name and must not be conflated: the nym-api INTERNAL v1 monitor (already spec'd as the `network-monitor` capability), and the standalone locust-driven `nym-network-monitor/` v2 crate (a separate, externally-driven monitor that is no longer in use, out of scope here).

## What Changes

- Introduce a new capability spec `network-monitors-contract` covering the CosmWasm authorisation registry end to end: the three-tier hierarchy and admin-at-instantiation, admin-only orchestrator authorise/revoke (with agent cascade-delete), orchestrator identity-key self-announcement (shape-only validation), orchestrator-only agent authorise (socket-keyed upsert), individual and wholesale agent revocation, the read/query surface (no single-address membership query), deterministic socket ordering, and the build-info-only migration.
- Introduce a new capability spec `nym-network-monitor` covering the v3 fleet and its ingest end to end: orchestrator startup gating and task set, the mixnet-contract-plus-self-description node registry, queue-less staleness-ordered testrun assignment, on-chain agent authorisation on announce, the two bearer-token HTTP surfaces, signed monotonic batch submission, stale/old-data eviction, and the four-table SQLite model; the agent one-shot lifecycle, bearer-only auth, two-hop self-loop probe mechanics, fixed-rate load test with dedup-by-id, the `reuse_header` bloomfilter-bypass replay, the `packets_sent = expected` back-pressure penalty, and the result shape; the mixnodes-only scope with the unwired gateway seam; the nym-api six-step ingest validation, per-entry drop-not-fail plus database dedupe, and the JSON-signed payload envelope; and a catalog of the downstream consumer surface (performance aggregation, provider, rewarding).
- Document the **node-side authorisation propagation** as part of the fleet capability: how nym-nodes load and event-subscribe to the contract's authorised-agent set, fold it into canonical-IP-keyed routing and Noise structures, and gate connection acceptance, packet routing, and the replay/bloomfilter bypass on it - and what that implies for propagation latency, revocation, and source-IP keying invariants.
- Document the **known limitations** as deliberate current-state facts: bearer-token (not per-request-signed) agent auth, source-IP-only replay-bypass gating, the absence of periodic node reconciliation against the contract (a missed revoke event only re-syncs on node restart), the in-memory agent registry re-announcing (and re-paying) on orchestrator restart, and the single-block gas ceiling on the contract's cascade delete.
- No code changes, no migrations, no new dependencies. This is a documentation-only deliverable ratifying the current implementation as the baseline. Any behaviour a reviewer judges to be an actual bug (rather than intended) becomes a follow-on change, not an edit to this spec.
