# node-status-api-monitoring Specification

> Generated by openlore on 2026-07-07
> Source files: `nym-node-status-api/nym-node-status-api/src/monitor/{mod,geodata,node_delegations}.rs`, `node_scraper/{mod,scraper,description,helpers,models}.rs`, `metrics_scraper/mod.rs`, `cli/mod.rs`

## Purpose

Defines the background data-ingestion workers of the node status service: the network monitor (directory + chain snapshot, geodata, delegations), the node scraper (self-reported descriptions and per-node packet stats), and the metrics scraper (per-gateway session metrics). Each runs on its own timed loop and writes into the shared PostgreSQL store consumed by the HTTP API.

## Requirements

### Requirement: The network monitor SHALL periodically snapshot the directory, geodata, and delegations

The monitor MUST run on a loop (default refresh 300s; 60s retry on failure). Each cycle MUST: check the ipinfo bandwidth allowance, fetch described nodes v2 from `nym-api`, classify gateways by declared entry/exit-IPR role, fetch bonded/basic/mixing nodes and families, write nym-nodes and families to the database, refresh geodata for every node (geolocating each IP via ipinfo, caching the first success with TTL `geodata_ttl`, else an empty location), build and write gateway records (including an `explorer_pretty_bond` with location and performance), refresh per-node delegations from `nyxd`, and write the network summary (8 summary keys plus `NetworkSummary`). A `run_once` early-exit mode MUST write only nodes and families.

#### Scenario: Full monitor cycle
- **GIVEN** reachable `nym-api`, `nyxd`, and ipinfo
- **WHEN** a monitor cycle runs
- **THEN** nym-nodes, families, geodata-enriched gateways, delegations, and the summary keys are all written to the database

#### Scenario: Geolocation failure yields empty location
- **GIVEN** a node whose IPs all fail geolocation
- **WHEN** the monitor refreshes geodata for it
- **THEN** it stores an empty `Location` rather than aborting the cycle

#### Scenario: Cycle failure retries
- **WHEN** a monitor cycle returns an error
- **THEN** the loop sleeps the 60s retry delay and retries

### Requirement: The description scraper SHALL fetch, sanitize, and normalize node self-descriptions

The description scraper MUST run every 4 hours with up to 5 concurrent tasks. Per node it MUST try the node's candidate contact URLs plus `/description`, deserialize the description response, **sanitize all HTML** (via `ammonia`), replace empty fields with `N/A`, and — when the moniker is empty — generate a deterministic three-word name derived from the node id, then upsert the description.

#### Scenario: HTML in a description is stripped
- **GIVEN** a node description containing HTML markup
- **WHEN** the description scraper processes it
- **THEN** the stored description has the HTML sanitized away

#### Scenario: Empty moniker gets a deterministic name
- **GIVEN** a node whose self-reported moniker is empty
- **WHEN** the description is stored
- **THEN** a deterministic three-word name derived from the node id is used

### Requirement: The packet-stats scraper SHALL fetch per-node stats and accumulate daily deltas

The node (packet-stats) scraper MUST run every 1 hour with concurrency from `packet_stats_max_concurrent_tasks` (default 10). Per node it MUST fetch `/stats` (parsing both legacy-mixnode and nym-node formats) and, for entry/exit gateways, fetch bridge client-params. Results MUST be batch-stored, and daily deltas MUST be computed against the previous raw stats row; on a counter decrease (node restart) it MUST use the current value rather than a negative delta.

#### Scenario: Daily delta across a restart
- **GIVEN** a node whose packet counter is lower than the previous raw reading (a restart)
- **WHEN** the daily delta is computed
- **THEN** the current value is used instead of producing a negative delta

### Requirement: The metrics scraper SHALL collect per-gateway session metrics directly from nodes

The metrics scraper MUST run every 6 hours (60s retry on failure). It MUST build the set of bonded+described nodes (skipping legacy mixnodes), connect directly to each node's own API, and fetch session metrics. Session data whose update time is the unix epoch MUST be treated as "no data" and dropped. Sessions MUST be split by session type (Vpn/Mixnet/Unknown) into duration arrays and stored; records older than the stale duration (1 year) MUST be deleted.

#### Scenario: Epoch update-time treated as no data
- **GIVEN** a node returning session metrics with an update time of the unix epoch
- **WHEN** the metrics scraper processes them
- **THEN** the data is dropped rather than stored

## Technical Notes

- **Implementation**: `monitor/mod.rs` (`Monitor::run`, `run_in_background`), `monitor/geodata.rs` (`IpInfoClient`, `Location`), `monitor/node_delegations.rs` (`DelegationsCache` behind `Arc<RwLock>`), `node_scraper/description.rs` + `scraper.rs` + `helpers.rs`, `metrics_scraper/mod.rs`.
- **External services**: `nym-api` (directory), `nyxd` chain (delegations), `ipinfo.io` (geolocation + bandwidth check), direct per-node HTTP APIs (descriptions, `/stats`, bridges, session metrics). Per-node errors are logged and skipped.
- **Caching**: node geodata cached in a shared `moka` cache keyed by node id with TTL `geodata_ttl` (default 86400s); delegations cached in an `Arc<RwLock<HashMap>>` swapped atomically each cycle and shared with the HTTP server.
- **Related specs**: writes into [[node-status-api-persistence]]; results served by [[node-status-api-http]].
