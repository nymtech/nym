## How search works [#how-search-works]

`search_docs` and `search_code` are semantic rather than keyword. Both sides of a comparison have to become vectors before similarity means anything, so the embedding happens in two places.

Each indexed Nym repository embeds its documentation sections and source files in its own CI and writes them to a shared index: the Nym docs and source on each change to the development branch, and the NymVPN client at each release. At call time, your query is embedded with the same model, and the server ranks the index against that vector by cosine similarity.

```text
your agent ──JSON-RPC──▶ /docs/api/mcp ──▶ embed the query
     ▲                         │                  │
     │                         │◀── query vector ─┘
     │                         │
     │                         ├─ rank the shared index by similarity
     │                         │
     └───── ranked sections ───┘
```

| Index | Model | Covers |
|---|---|---|
| Documentation | `voyage-3-large` | every published docs page, chunked by section, and the NymVPN client's Markdown docs |
| Source code | `voyage-code-3` | selected Nym crates (SDK, wasm, Sphinx, smolmix, and their examples) and the NymVPN client: its core, the desktop, Android and Apple apps, and its WireGuard netstack |

The code index uses a model trained on source rather than prose. That is why `search_code` surfaces implementation details a prose model ranks poorly, and why the two indexes are kept separate instead of merged.

Query and index must come from the same model. A query embedded with one model and scored against an index built with another returns neighbours that are not meaningfully related.

A search costs one embedding call for your query and one similarity scan of the index. Your query text goes to the embedding provider (Voyage AI) to make its vector. Nothing else about the request does.
