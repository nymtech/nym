# Routing a browser or WebView app

Requests leave a browser or WebView app from several places. Your own `fetch` helper is
one. Libraries that call the global `fetch` are another. So are cross-origin
iframes, vendor SDKs and Web Workers. Only your own helper is yours to redirect.

A WebView host runs the same web platform as a browser tab, so everything below
applies to both. Capacitor, Cordova, WKWebView and Android WebView are in scope.

A routing policy written in application code therefore binds less than it
appears to. When it fails to bind, you get no error. The request succeeds, it
returns the data you expected, and it travels over the clearnet.

This page covers those failures and what to do about them.
[Planning an integration](/developers/integrating) decides *what* to route. This
page assumes that you have that list, and that you want to make it true.

## Why patching fetch does not cover your app

A single module that wraps `fetch`, imported in twenty places, looks like a
choke point. Two things stop it being one. Neither announces itself.

**The wrapper only binds code that imports it.** JavaScript resolves a bare
identifier by scope, not by intent. A call site that forgot the import still
compiles and still runs:

```js
// There is no `fetch` in scope here. The bare identifier resolves to the global
// `window.fetch`, so this request never reaches the routing policy.
return useRemoteData({ fetch, isOffline, ...props })
```

A bare `fetch` passed as a property in an options bag reads as covered. The
request returns real data and nothing fails. The only visible sign is in the
network panel. You see an `HTTP/2` connection and a round trip of tens of
milliseconds. No mixnet request produces that. Search for the bare identifier,
not only for the import.

**Libraries bring their own transport.** A library that does its own networking
does not touch your wrapper. Ethers is one example: it calls the global `fetch`
from its own web layer. To route its traffic you subclass the provider and
override `send()`. No work on a fetch helper reaches it. The same holds for any
client with its own adapter layer, such as `axios`, `got`, or a generated API
client.

Audit the transports in your dependency tree, not the call sites in your own
code. Then check by hand for anything built outside your routed factory. That
code is unrouted by construction. A provider constructed directly with a
hardcoded URL is the common case, and it usually sits near the bottom of a
config file.

## What cannot be routed from a web runtime

Some traffic is unreachable from your JavaScript, however carefully you work.
Being explicit about this matters more than the part that works, because it is
what your users are still exposed to.

| Source | Why it is out of reach |
|---|---|
| Cross-origin iframes | A separate browsing context with its own networking. Embedded swap widgets, on-ramp providers and dApp frames route nothing through your code. |
| Vendor SDKs in their own contexts | Payment and identity providers, analytics loaders, and connect libraries that open their own windows or frames. |
| Third-party WebSocket relays | [`mix-websocket`](/developers/mix-websocket) carries `ws` and `wss`, but its constructor is asynchronous and it exposes no `bufferedAmount`. To drop it in for a synchronous `WebSocket` inside someone else's library, you write an adapter for that library. |
| Hardware wallets | Some paths are local and touch no network at all (WebHID, WebUSB). Others reach out from a vendor-hosted page that you do not control. |
| Browser-initiated requests | `navigator.sendBeacon`, `EventSource`, `<img>` and `<script>` sources, and prefetch hints. |

A destination in that table may learn something you want to hide. Transport is
then the wrong layer to fix it at. Drop the integration, move it behind your own
backend, or record it as accepted in your threat model.

## Detecting requests that bypass the policy

Wrap `window.fetch` and `XMLHttpRequest.prototype.open` at startup. Treat any
direct request to a routed host as a leak. The mixnet path never touches those
globals for those hosts. A hit is therefore a bug in your own code every time,
with no false positives to triage. It catches the bare-identifier bypass above
the moment it fires.

```js
const ROUTED_HOSTS = new Set(['api.example.com'])
const FAIL_CLOSED = false

function isRouted(url) {
  return ROUTED_HOSTS.has(new URL(url, location.href).hostname)
}

function onLeak(url) {
  console.error('nym leak guard: direct request to routed host', url)
  if (FAIL_CLOSED) throw new Error(`blocked direct request to ${url}`)
}

export function installLeakGuard() {
  const nativeFetch = window.fetch
  window.fetch = function (input, init) {
    const url = input instanceof Request ? input.url : String(input)
    if (isRouted(url)) onLeak(url)
    return nativeFetch.call(this, input, init)
  }

  const nativeOpen = XMLHttpRequest.prototype.open
  XMLHttpRequest.prototype.open = function (method, url, ...rest) {
    if (isRouted(String(url))) onLeak(String(url))
    return nativeOpen.call(this, method, url, ...rest)
  }
}
```

`FAIL_CLOSED` is the same decision as
[fail-open or fail-closed](/developers/integrating#decide-fail-open-or-fail-closed-explicitly),
made one request at a time. Left off, the request still goes out, and you find
out afterwards. Turned on, the throw propagates to whoever called `fetch`. That
stops the leak. It also surfaces as a network error in code that did not expect
one. Run it on in development.

Log once at install time as well, whatever you choose. Otherwise "no leaks
reported" and "the guard was never installed" produce identical output. The
first is the claim you will want to make.

The guard does not see `navigator.sendBeacon`, `EventSource`, `WebSocket`,
`<img>` and `<script>` sources, or anything inside a cross-origin iframe. Those
need enforcement, below.

## Proving the mixnet did the work

A leak guard proves that your code ran. It says nothing about whether the tunnel
carried anything. To test that, ask one echo service over both paths and compare
what it saw:

```js
const sourceIp = async (get) => (await (await get('https://echo.example/ip')).json()).ip

const [clearnet, mixnet] = await Promise.all([
  sourceIp((u) => fetch(u)),
  sourceIp((u) => mixFetch(u)),
])

console.log({ clearnet, mixnet, differ: clearnet !== mixnet })
// { clearnet: "203.0.113.9", mixnet: "51.x.x.x", differ: true }
```

Hang it somewhere you can reach from the console. Nothing else separates a
request that went through the tunnel from transport code that ran without
throwing.

## Enforcing with Content Security Policy

`connect-src` is the only browser-enforced answer. The mechanism behind it is
not obvious. Mixnet payload traffic never reaches CSP as a connection to your
destination. It is a WebSocket to a Nym gateway, and the TLS session terminates
inside the WASM. So leave the routed host out of `connect-src`. Every direct
path to it is then blocked, and the mixnet path keeps working.

That combination is the proof. A request succeeds, while the browser refuses
every direct connection to its destination. It can only have come through the
tunnel.

```text
connect-src 'self' wss: https://validator.nymtech.net
            https://cdn.example.com https://prices.example.com;
worker-src 'self' blob:;
```

`worker-src 'self' blob:` is required. `mix-tunnel` base64-decodes its Web
Worker and starts it from an object URL. With no `worker-src`, CSP falls back to
`script-src` and the browser blocks it. Raise the cost of that in review,
because `blob:` permits worker code that did not come from your origin.

`wss:` has to stay broad. Gateway hostnames come from the network topology at
runtime, so you cannot enumerate them in advance.

### The nym-api bootstrap is policed even though payload traffic is not

Payload traffic is invisible to `connect-src`. The client's own bootstrap is
not. Before any mixnet traffic exists, the client fetches the network topology
from the nym-api over ordinary HTTPS, and uses it to pick a gateway. That
request answers to the policy like any other.

Leave it out, and the tunnel dies at startup with a gateway selection error. The
error never mentions CSP. On mainnet the host is `https://validator.nymtech.net`.

Enforcement must therefore allow the control plane and still deny the data
plane's destination. They are different hosts, which is the only reason this
works.

<Callout type="warning">
CSP is an allowlist, so you cannot deny a single host. Leaving your routed
destination out means enumerating every other destination the app uses, and
keeping that list current. Getting it wrong fails in an ugly direction. Add an
endpoint anywhere in the app and forget the list. The browser then blocks it in
production, after it worked in every local test that carried no policy.

Two mitigations. First, roll out with `Content-Security-Policy-Report-Only` as a
*header*, which a `<meta>` tag cannot express. Collect violations from real
sessions instead of guessing at the list. Second, check for a policy already set
server-side. Multiple policies intersect and the narrower one wins. A header
that carries `default-src` or `script-src` without `blob:` therefore defeats
anything you change in a `<meta>` tag.
</Callout>

## Use an incomplete policy to map your egress surface

Turning enforcement on is the cheapest way to find out what your app talks to.
Run with a deliberately incomplete `connect-src` and read the violations as a
map. Expect it to name destinations that appear in no config file.

## Keeping the WASM out of your initial payload

Pull the Nym packages in with a dynamic `import()` behind a named chunk. They
are then fetched when the mixnet is first used, and never land in the initial
bundle:

```js
let tunnelPromise

export function ensureTunnel() {
  tunnelPromise ??= import(/* webpackChunkName: "nym-mixnet" */ '@nymproject/mix-tunnel')
    .then((m) => m.setupMixTunnel({ /* opts */ }))
  return tunnelPromise
}
```

Memoising the promise does more than tidy the code. The tunnel is one-shot per
page, and a second `setupMixTunnel` call rejects.
[The guidance](/developers/mix-tunnel/guides#tunnel-state) is therefore to guard
on `getTunnelState()`. That guard races. Two call sites can check while the
state is `connecting`, and both then call setup. One of them takes the
rejection. A memoised promise has no such window. It also hands concurrent
callers one bring-up to await, instead of a state to poll.

Add one thing before you ship it. `??=` caches a rejection as durably as it
caches a success. A chunk that fails to load once leaves every later caller
awaiting that rejection for the life of the page. So does a `setupMixTunnel`
that rejects because something else brought the tunnel up first. Clear
`tunnelPromise` in a `catch`, so that the next call retries.

### Build notes that recur

Expect several megabytes gzipped for the chunk. Expect a slower first compile if
a large inlined module goes through your transpiler. Two things are easy to
miss:

- Turn source maps off while you work on the integration
  (`GENERATE_SOURCEMAP=false` under Create React App, or your bundler's
  equivalent). Mapping an inlined WASM blob is pure cost.
- Minification is the memory-hungry step, because the worker arrives as one long
  base64 line. A build that dies with a bare `Killed` was stopped by the
  out-of-memory killer, not by a code error. Development builds do not minify,
  and are lighter.

If your build disables code splitting on purpose, weigh the exception rather
than assuming it. A stale lazy chunk disables the mixnet until the user reloads.
A stale main bundle breaks the app. The blast radius is therefore contained. It
does mean keeping old chunks for as long as sessions outlive a deployment.

## Feature flags read from localStorage are per origin

`localStorage` is scoped to an origin. A flag set on `http://localhost:3000`
does not exist on `http://127.0.0.1:3000`. Combine that with logging gated on
the same flag, and the integration appears to do nothing, for a reason unrelated
to the mixnet.

Accept a query parameter override that writes through to `localStorage`. Log the
resolved configuration at startup, whatever the flag says, so an unset flag
shows up instead of going quiet. See
[make the privacy flag announce itself](/developers/integrating#make-the-privacy-flag-announce-itself-unconditionally).
