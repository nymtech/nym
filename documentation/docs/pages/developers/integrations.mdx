# Choosing an Approach

Any application that integrates with Nym sends its traffic through the mixnet via a Nym client. The right package depends on two factors: your **environment** (where your code runs) and your **architecture** (whether you control both sides of the communication).

## At a glance

|   | **End-to-end** (both sides run Nym) | **Proxy mode** (Nym → clearnet exit) |
|---|---|---|
| **Rust** (native / desktop / CLI) | [`nym-sdk`](/developers/rust) (Stream, Mixnet, Client Pool) | [`smolmix`](/developers/smolmix) (`TcpStream` / `UdpSocket`) · [`nym-sdk` SOCKS client](/developers/rust) |
| **TypeScript** (browser) | [TypeScript SDK](/developers/typescript) (`@nymproject/sdk` raw messaging) | [`mix-fetch`](/developers/mix-fetch) (HTTP/S) · [`mix-dns`](/developers/mix-dns) (UDP DNS) · [`mix-websocket`](/developers/mix-websocket) (WS/WSS) |
| **Mobile** (iOS / Android) | via [`nym-vpn-client`](#mobile) (uniffi + cargo-swift / cargo-ndk) | via [`nym-vpn-client`](#mobile) (uniffi + cargo-swift / cargo-ndk) |

## Environment

Different runtimes have different transport constraints: a browser cannot open raw sockets or access the filesystem, while a desktop app can.

- **Native / Desktop / CLI**: full access to system networking and persistent storage. Use [`nym-sdk`](/developers/rust) for end-to-end messaging or byte streams, or [`smolmix`](/developers/smolmix) for `TcpStream`/`UdpSocket` access in proxy mode.
- **Browser**: restricted to WebSockets, Web Transport, and `fetch`; HTTPS-only mixed-content rules; no filesystem access. The mix-* packages share one mixnet tunnel ([`mix-tunnel`](/developers/mix-tunnel)) and split by protocol: [`mix-fetch`](/developers/mix-fetch) for HTTP/S, [`mix-dns`](/developers/mix-dns) for UDP DNS, [`mix-websocket`](/developers/mix-websocket) for WS/WSS. For end-to-end messaging where you control both sides, use the [TypeScript SDK](/developers/typescript).

### Mobile

There is no first-party mobile SDK; you compile the Rust SDK to the mobile targets yourself. A [`uniffi`](https://mozilla.github.io/uniffi-rs/) wrapper exposes a foreign-function interface, and from there [`cargo-swift`](https://github.com/antoniusnaumann/cargo-swift) builds an iOS XCFramework (consumed via SwiftPM) while [`cargo-ndk`](https://github.com/bbqsrc/cargo-ndk) builds Android `jniLibs/` (driven from Gradle).

### Android TLS workaround

On Android the client can fail to bootstrap the mixnet when the validator API serves a Let's Encrypt certificate with no OCSP responder URL (`validator.nymtech.net` is one): `rustls-platform-verifier` routes through Java's `CertPathValidator`, which raises a hard `Revoked` / "Certificate does not specify OCSP responder" error before its soft-fail policy can apply, so every API call fails. iOS and the desktop targets are unaffected (they tolerate or skip the check). The fix is a `cfg(target_os = "android")` shim in `common/http-api-client/src/registry.rs` that routes `default_builder()` through `use_preconfigured_tls` with `webpki_roots::TLS_SERVER_ROOTS` (no revocation check), leaving other targets on the platform verifier; about 25 lines plus a `webpki-roots` dependency. An upstream fix ([rustls-platform-verifier#179](https://github.com/rustls/rustls-platform-verifier/pull/179)) would let it be dropped.

## Architecture

The second factor is whether you control both sides of the communication.

**End-to-end (E2E)**: both sides run Nym clients. All traffic stays Sphinx-encrypted the entire way. Appropriate for peer-to-peer setups or any case where you control both endpoints.

![](/images/developers/nym-arch-client-to-client.png)

**Proxy**: only the client side runs Nym. Traffic exits the mixnet at an Exit Gateway and continues to the destination over the public internet. The mixnet anonymises the sender; payload protection (TLS, Noise, etc.) is your application's job, as on a direct connection. Appropriate when connecting to third-party services such as blockchain RPCs or external APIs.

![](/images/developers/nym-arch-ip-routing.png)

<Callout type="warning">
Once traffic leaves the Exit Gateway, it travels over the public internet to the destination, exactly like any other server-initiated connection. The mixnet anonymises the sender but does not encrypt the payload past the gateway. Use TLS or another application-layer cipher as you would on a direct connection. See [Exit Gateway Services](/network/infrastructure/exit-services) for what the exit can and cannot observe.
</Callout>

**Browser apps**: both proxy and E2E modes work slightly differently in a browser setting. The Nym client runs as a WASM blob inside a Web Worker, and your application communicates with it via JS bindings rather than direct function calls. The mixnet behaviour is identical; the integration shape differs.

![](/images/developers/nym-browser-arch.png)

## Browser packages, one tunnel

The three browser proxy-mode packages ([`mix-fetch`](/developers/mix-fetch), [`mix-dns`](/developers/mix-dns), [`mix-websocket`](/developers/mix-websocket)) share a single mixnet tunnel via [`mix-tunnel`](/developers/mix-tunnel). Calling `setupMixTunnel()` once brings up one WASM instance, one IPR connection, and one userspace TCP/IP stack; all three packages route through it. There's no per-package handshake cost.
