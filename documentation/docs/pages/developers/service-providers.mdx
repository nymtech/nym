# Building a Nym Service Provider

A **service provider** is your own server-side application with a Nym client embedded in it. Clients address that client directly over the mixnet, your code answers, and it never learns who asked.

The embedding is the whole distinction, and it decides which of the [two approaches](/developers#end-to-end-or-proxy) you are in:

- **You cannot change the service.** That is proxy mode. An Exit Gateway leaves the mixnet on your behalf and connects to it over ordinary clearnet, subject to that gateway's [exit policy](/network/infrastructure/exit-services#the-exit-policy-applies).
- **You can change the service.** That is end-to-end. You put a Nym client inside it, so there is no Exit Gateway, no clearnet hop, and no exit policy to satisfy. Traffic stays Sphinx-encrypted the whole way.

This page is the second case. It assumes you own the server code and are willing to modify it, which in practice means adding a mixnet client alongside whatever transport it already speaks and routing requests in from there.

Everything downstream follows from that choice: the process can sit in a DMZ with no inbound access at all, its Nym address becomes the only way to reach it, and replies go back over [SURBs](/network/mixnet-mode/anonymous-replies) rather than an open connection.

## The fourth participant

Nym's infrastructure is three kinds of node: validators, gateways, and mix nodes. A service provider is a fourth kind of participant, and it is not infrastructure at all. It is a third party that makes itself reachable *through* the mixnet.

Two systems are in play, and only one of them changes:

```
mixnet ──▶ your app + embedded Nym client ──▶ backend it already talks to
              (this is what you modify)         (unchanged, no Nym awareness)
```

Your application gains a Nym client. Whatever it calls downstream, a database, an RPC node, a payment network, needs no awareness of Nym whatsoever: it sees ordinary local calls from your process, exactly as before. The whitepaper's example is a provider relaying Bitcoin transactions to the Bitcoin peer-to-peer network, which knows nothing about any of it.

It is also distinct from the [exit gateway services](/network/infrastructure/exit-services) Nym itself operates. The Network Requester and IP Packet Router are general-purpose exits, run by gateway operators, forwarding to arbitrary clearnet destinations. A service provider serves one application, and you are the one running it.

## It never accepts an inbound connection

A service provider is an ordinary mixnet client. It dials **out** to its gateway and pulls messages from it.

```
       your service provider
                │
                │  outbound only, client-initiated
                ▼
           its gateway  ◀────── mix layers ◀────── client
```

Two consequences worth designing around:

- It can run behind a deny-all firewall, in a DMZ, or on a machine with no public IP. Its Nym address is the only way to reach it.
- The gateway is the part that needs to be publicly reachable and stable. That is the reverse of the usual arrangement, and it drives the addressing section below.

## Replying without knowing who asked

Requests arrive as ordinary Sphinx packets, but each carries something extra: a bundle of single-use reply blocks (SURBs) that the client pre-computed before sending. A SURB is an encrypted Sphinx header describing a return route ending at the client. The provider attaches its reply to one and hands it back to the mixnet.

Because the SURB is encrypted by the *sender*, the provider can read nothing from it: not the route, not the per-hop delays, not the client's address. Reply packets are indistinguishable from forward packets, so requests and replies share one anonymity set.

See [Anonymous Replies](/network/mixnet-mode/anonymous-replies) for the mechanics, including replenishment and the single-use constraint.

## The receive-and-reply loop

The whole pattern is one loop. Working examples live in the [`nym-sdk` examples directory](https://github.com/nymtech/nym/tree/develop/sdk/rust/nym-sdk/examples); `surb_reply.rs` is the one to read first.

```rust
use nym_sdk::mixnet::{
    AnonymousSenderTag, MixnetClientBuilder, MixnetMessageSender, StoragePaths,
};
use std::path::PathBuf;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // Persistent storage, not `MixnetClient::connect_new()`. The convenience
    // constructor builds an ephemeral client, which generates a fresh identity
    // on every run: the address you handed out yesterday stops working today.
    // A service provider has to keep its keys.
    let paths = StoragePaths::new_from_dir(PathBuf::from("./sp-storage"))?;
    let mut client = MixnetClientBuilder::new_with_default_storage(paths)
        .await?
        .build()?
        .connect_to_mixnet()
        .await?;

    println!("service provider listening on {}", client.nym_address());

    while let Some(messages) = client.wait_for_messages().await {
        for msg in messages {
            // An opaque token derived from the SURBs bundled with the request.
            // It is what lets us reply without learning the sender's address.
            let Some(return_to): Option<AnonymousSenderTag> = msg.sender_tag else {
                // No SURBs attached, so there is no return route. Nothing to do.
                continue;
            };

            let response = handle_request(&msg.message).await?;
            client.send_reply(return_to, response).await?;
        }
    }
    Ok(())
}
```

`handle_request` is where your application lives. It runs locally, against a backend that knows nothing about Nym, and its result goes back through the mixnet.

### Three ways a client reaches it

The provider is one half of a conversation, and the other half can be written three ways. Two of them put the same thing on the wire, so the loop above serves both. The third does not.

| Client | What it puts on the wire | Provider side |
|---|---|---|
| [`nym-sdk` mixnet messaging](/developers/rust) (Rust) | discrete mixnet messages | the loop above |
| [`@nymproject/sdk`](/developers/typescript) (browser TypeScript) | discrete mixnet messages | the loop above |
| [`nym-sdk` Stream module](/developers/rust) (Rust) | a framed, ordered byte stream | `listener()` / `accept()`, below |

The first two differ only in language. A browser client calls `client.send({ ... })` and subscribes to received events, a Rust client calls `send_message` and `wait_for_messages`, and the provider cannot tell them apart because both produce ordinary mixnet messages carrying SURBs.

The Stream module is a different protocol on top of those messages: it adds sequence numbers, reassembly, and stream framing, so bytes arrive in the order they were written. A provider expecting messages will not understand a stream, and the reverse holds too. **Decide which one your clients use before you write the provider**, because it changes the receive loop:

```rust
// Stream-shaped provider. `listener()` activates stream mode and may only be
// called once per client, so this replaces the wait_for_messages loop above
// rather than sitting alongside it.
let mut listener = client.listener()?;

while let Some(stream) = listener.accept().await {
    tokio::spawn(async move {
        // MixnetStream implements AsyncRead + AsyncWrite, so ordinary tokio I/O
        // works unchanged and framing comes free from the trait.
        let (mut reader, mut writer) = tokio::io::split(stream);
        // ... read a request, write a response
    });
}
```

Choose messaging when requests stand alone: a broadcast, a one-shot query, a notification. Choose Stream when the exchange has a sequence to preserve, or when you want to reuse code that already expects `AsyncRead`/`AsyncWrite`. The [nym-sdk page](/developers/rust#which-module-do-i-need) covers the trade in more detail.

Note that a browser client has no Stream option today, so if any of your clients are web-based, messaging is the choice that serves all three.

## Your address is only as stable as its gateway

Clients reach a provider by its [Nym address](/network/reference/addressing), the value the sketch prints at startup:

```text
<identity-key>.<encryption-key>@<gateway-identity-key>
```

Three parts: a base58 Ed25519 identity key that routes to the client, the public key that encrypts the final Sphinx layer, and the identity of the gateway holding the client's messages.

That last component has an operational consequence. The gateway identity is baked into the address, so **if the gateway disappears, every copy of your address stops working**. Persistent storage keeps your keys, but it cannot keep someone else's gateway online.

To guarantee a stable address, run your own mainnet gateway and register your provider with it. Two things to be clear about:

- The gateway must **not** be in the DMZ. It needs a static, stable, publicly routable IP. The provider behind it is the part that hides.
- A gateway you run is still a public gateway. Every gateway in the network is available to every user, so you cannot operate one exclusively for your own clients.

There is deliberately no discovery system for Nym addresses, because clients should not be enumerable. Distribute the address out of band: ship it in your client's configuration rather than looking it up.

## The default sending budget

A mixnet client sends on a Poisson schedule, and that schedule is a fixed budget whether or not you have anything to say. The defaults in [`client-core`](https://github.com/nymtech/nym/blob/develop/common/client-core/config-types/src/lib.rs) are one real packet every 20 ms on average (50 per second) plus one loop cover packet every 200 ms (5 per second), so roughly 55 packets per second in total. A regular Sphinx packet carries a 2 KB payload.

Three things follow:

| | |
|---|---|
| **Capacity is shared** | Every reply to every client comes out of the same ~50 packets per second. One provider client serves only so many users. Measure your reply sizes and provision more clients when the budget runs out. |
| **Idle is not free** | With nothing real to send, the client sends cover packets instead: same size, same rate, same Sphinx processing. An idle provider pays nearly the full bandwidth and CPU bill. |
| **It never stops** | The client sends constantly, for as long as the provider is up, and its gateway forwards that stream constantly too. |

These are configuration, not physics. A client built through the SDK can override every one of them, including turning off Poisson pacing (`disable_main_poisson_packet_distribution`) and the cover stream (`disable_loop_cover_traffic_stream`), both of which default to on. The cost is privacy: without them, the shape of your traffic starts to reflect your real activity.

## What this is not for

Every reply packet consumes one SURB, and the client has to pre-compute and send those SURBs up front. That suits request-response traffic with small answers: a transaction broadcast, a balance query, a status check.

It does not suit bulk transfer. Syncing a chain, streaming media, or anything else measured in megabytes will exhaust the SURB budget and the sending rate long before it finishes. See [What Nym Cannot Do](/developers/limitations) for where the limits actually bite, and [nym-smoldvpn](/developers/smoldvpn) for the tunnel-shaped alternative when the workload is bulk rather than request-response.
