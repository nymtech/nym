# node-status-agent Specification

## Purpose

`nym-node-status-agent` is a CLI worker that pulls test assignments from one or more node status API servers, runs network probes against Nym gateways using the in-process `nym-gateway-probe` library, and submits ed25519-signed results back. It is a one-shot binary — each invocation runs a single subcommand and exits — looped externally by its container entrypoint. The `nym-node-status-client` library provides the signed request/response contract it uses to talk to the API.

## Requirements

### Requirement: The agent SHALL provide run-probe, run-ports-check, and generate-keypair subcommands

The CLI MUST expose three subcommands:

- **`run-probe`** — takes one or more `--server <address|port>` values (repeatable) and flattened probe-config overrides; requests a probe test run and submits results.
- **`run-ports-check`** — takes `--server` values, `--min-gateway-mixnet-performance`, `--ignore-egress-epoch-role`, and netstack args; requests a ports-check test run and submits results.
- **`generate-keypair`** — takes an optional `--path` (default `private-key`) and writes a new ed25519 keypair.

The `run-probe` and `run-ports-check` subcommands MUST require the `NODE_STATUS_AGENT_AUTH_KEY` environment variable (a base58 ed25519 private key); a missing or invalid key MUST be a hard error. A `--server` value MUST be exactly two `|`-separated parts (`address` and a `u16` port); malformed values MUST be rejected.

#### Scenario: Missing auth key
- **GIVEN** `run-probe` is invoked without `NODE_STATUS_AGENT_AUTH_KEY` set
- **WHEN** the agent parses its server configuration
- **THEN** it fails with an error rather than contacting any server

#### Scenario: Malformed server argument
- **WHEN** `--server` is given a value that is not `address|port` with a valid `u16` port
- **THEN** parsing fails with an error

### Requirement: The first server SHALL be the primary and testruns SHALL be requested only from it

When multiple `--server` values are given, the agent MUST treat the first as the "primary" and request a test-run assignment only from the primary. A fresh signing client MUST be built per server (cloning the private key). Result submissions MUST fan out to all configured servers concurrently.

#### Scenario: Assignment requested from primary only
- **GIVEN** three `--server` values
- **WHEN** the agent requests a test run
- **THEN** it queries only the first (primary) server for the assignment, but submits the result to all three

### Requirement: The run-probe workflow SHALL request, run in-process, capture logs, and submit signed results

For `run-probe` the agent MUST: request a test run from the primary; on `None` (no work available) log and exit `Ok` without probing; on a valid assignment parse the base58 gateway identity key, read the network from env, build the probe via `Probe::new_for_agent`, convert attached ticket materials into credential args, start log capture, run `probe_run_agent` in-process, stop and drain the captured logs, and submit the `ProbeResult` plus captured log to all servers. Log capture MUST only buffer tracing output emitted between `start()` and `stop_and_drain()` (i.e. during the probe run).

#### Scenario: No testruns available
- **GIVEN** the primary returns "no testruns available" (HTTP 503)
- **WHEN** the agent requests a test run
- **THEN** it logs the condition and exits successfully without running the probe or submitting anything

#### Scenario: Logs captured only during the probe run
- **GIVEN** an assigned test run
- **WHEN** the agent brackets the probe run with `log_capture.start()` / `stop_and_drain()`
- **THEN** only tracing output emitted during the run is captured and submitted with the result

### Requirement: The run-probe submission SHALL use v1 for the primary and v2-with-context for secondaries

When submitting probe results, the agent MUST send the primary server (index 0) a v1 `submit_results` (probe log truncated to 1024 bytes, `POST /internal/testruns/{id}`), and each secondary server (index > 0) a v2 `submit_results_with_context` (`POST /internal/testruns/{id}/v2`, including the gateway identity key, log not truncated). Per-server submission failures MUST be logged as warnings and MUST NOT abort submission to the other servers.

#### Scenario: Mixed submission versions
- **GIVEN** a primary and one secondary server
- **WHEN** the agent submits results
- **THEN** the primary receives the v1 endpoint with a ≤1024-byte log and the secondary receives the v2 endpoint carrying the gateway identity key

#### Scenario: One server failing does not block others
- **GIVEN** two servers where one submission fails
- **WHEN** results are fanned out
- **THEN** the failure is logged as a warning and the other server still receives its submission

### Requirement: The run-ports-check workflow SHALL force the exit-policy port set and enforce a hard timeout

For `run-ports-check` the agent MUST request a ports-check assignment (treating both "no testruns available" and HTTP 404 as "no work"), force the netstack port list to the full `EXIT_POLICY_PORTS`, and run the scan under a 90-minute (5400s) hard timeout. On timeout it MUST log an error with gateway/testrun context and return an error without submitting. On success it MUST submit the `PortCheckResult` with context to **every** server (including the primary) via `POST /internal/testruns/{id}/ports-check/v2`.

#### Scenario: Ports-check endpoint absent
- **GIVEN** a server without the ports-check endpoint (HTTP 404)
- **WHEN** the agent requests a ports-check assignment
- **THEN** it treats it as no work and skips the iteration

#### Scenario: Scan exceeds hard timeout
- **GIVEN** a port scan that runs longer than 5400s
- **WHEN** the timeout elapses
- **THEN** the agent logs an error and returns without submitting results

### Requirement: generate-keypair SHALL emit base58 keys and prompt whitelisting

The `generate-keypair` subcommand MUST create a fresh ed25519 keypair, write the base58-encoded private key to the given path, and write the base58-encoded public key to a sibling file named `public-key`. It MUST log that the public key needs to be whitelisted with the node status API.

#### Scenario: Keypair written to disk
- **WHEN** `generate-keypair --path keys/private` runs
- **THEN** the base58 private key is written to `keys/private`, the base58 public key to `keys/public-key`, and a whitelisting reminder is logged

### Requirement: All API requests SHALL be ed25519-signed over a bincode canonicalization

The client MUST sign every request payload by bincode-serializing it and signing the bytes with the agent's private key, embedding the agent public key inside the signed payload so the server can verify the signature and check the key against its whitelist. There MUST be no bearer-token or TLS-client-cert auth. Request bodies MUST be sent as JSON while the signed portion uses bincode as the canonical form; request timestamps MUST use the current unix time.

#### Scenario: Signed request envelope
- **WHEN** the agent requests a test run
- **THEN** it sends a JSON body containing `{agent_public_key, timestamp}` and an ed25519 signature computed over the bincode serialization of that payload

## Technical Notes

- **Implementation**: agent `cli/{run_probe,run_ports_check,generate_keypair}.rs`, `common.rs` (primary/build-client helpers), `log_capture.rs` (tracing `MakeWriter` capture); client `lib.rs` (`NsApiClient` methods), `auth.rs` (`SignedRequest`/`VerifiableRequest`), `models.rs` (request/response DTOs).
- **Probe invocation**: in-process library calls (`Probe::new_for_agent`, `probe_run_agent`, `run_ports_for_agent`) — not a subprocess. See [[gateway-probe]].
- **No retries**: each subcommand is a single attempt; re-invocation is provided by the external `entrypoint.sh` loop with `SLEEP_TIME`. See [[architecture]].
- **Client protocol** (base URL `{address:port}`): `GET /internal/testruns`, `GET /internal/testruns/ports-check`, `POST /internal/testruns/{id}`, `POST /internal/testruns/{id}/v2`, `POST /internal/testruns/{id}/ports-check/v2` — the server side of these is [[node-status-api-testruns]].
- **Ticket materials**: assignments carry `AttachedTicketMaterials`, converted to `CredentialArgs` via a versioned serialiser at the current revision; the agent's `TestrunAssignmentWithTickets` redacts ticket data in its `Debug` impl.
