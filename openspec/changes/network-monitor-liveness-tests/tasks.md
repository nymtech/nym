## 1. Provisional defaults and the one compatibility check

- [x] 1.1 Adopt the provisional liveness profile defaults (50 packets per target, a PER-TARGET rate of 50 packets/second, a 5 second straggler wait, wave sizes of 100 mixnode and 50 gateway targets) and make every one of them CLI- and env-overridable, so an agent host that cannot sustain a full wave is a configuration change rather than a code change. The rate sits well below the stress profile's 1000/s so that no target is under load, and puts a target's send window at about one second, since a probe asking whether a node forwards at all has no reason to hold one open longer. A full wave's aggregate is consequently 5000/s (~15 Mbps at `AckPacket` sizing) for that second, above a stress run's rate but a sixth of its volume; the aggregate is deliberately left to scale with the orchestrator's wave size rather than being capped agent-side
- [x] 1.2 Size the liveness lease budget, straggler wait and per-target timeout from those defaults with slack, and make them configurable on the same terms, with no behaviour depending on a specific value. A 30 second per-target timeout fits inside the orchestrator's existing 1 minute lease, which the profile already satisfies without change: ~1 second of sending plus the straggler wait plus TCP and Noise setup, all concurrent across the wave, so the deadline is dominated by setup rather than by sending
- [ ] 1.3 Confirm on a devnet that an un-upgraded node still ingests an `AuthoriseNetworkMonitor` carrying an unknown field, rather than logging a parse failure and skipping it. The `cw_serde` reading says it will; this assumption is load-bearing for every future contract change and gates the orchestrator deploy, not the migration, which emits no message at all

## 3. Shared request/response types

- [x] 3.1 Add a `TestKind` enum (`stress`, `liveness`) to `nym-network-monitor-orchestrator-requests`
- [x] 3.2 Replace `TestRunAssignment` with a kind-tagged assignment carrying per-kind payloads: mixnode-stress and mixnode-liveness (node address, node ips, noise key, sphinx key, key rotation id) and gateway-liveness (additionally the client websocket port). Three points superseded the original wording. The `stress` variant is named `MixnodeStress`, because a gateway stress test would not resemble the mixnode one and the (kind, role) pairing is not one-to-one. No `probe profile` is carried: the spec puts every profile value in the agent's own CLI/env-overridable config, and the kind tag already selects which set to apply, so a profile field would be a second source of truth with no defined behaviour if the two disagreed. The node's ed25519 identity sits on the SHARED mixnet payload rather than only on the gateway one: every bonded node has one, so it costs no eligibility constraint, and it is what a future signature check over a node's responses would verify against
- [x] 3.3 Make the assignment response carry a wave (a list of targets) for liveness and a single target for stress, with an empty response still meaning "no work". A wave is HOMOGENEOUS in tested role, which follows from the variants being per (kind, role) rather than per kind: the two liveness probes are different machinery, so a dual-role node is assigned each role separately. "No work" stays the absent assignment on the response; an empty wave is documented as never emitted rather than given a helper, since the orchestrator is the only party that could emit one and it enforces the invariant at the point it builds the wave
- [x] 3.4 Add a per-signal result shape (`signal` discriminator plus the existing counts, handshake durations and latency distributions) and make the submission request carry the run-level fields plus one or more signals. RENAMED throughout: the shape is `InterfaceMeasurement` discriminated by `ExercisedInterface`, with values `mix_forwarding` / `client_ingest` / `client_delivery` superseding Decision 8's `gw_ingress` / `gw_egress`. "Signal" was rejected as borrowed from another domain and not implying its representation, and route-shaped names (`path`, `leg`, `section`) were rejected because every value traverses the mixnet, so geometry does not distinguish them - the discriminator names the node FUNCTION exercised. The test kind never appears in a value: the kind is a property of the run, sits on the parent row, and duplicating it into the discriminator would make `(kind=stress, interface=liveness_*)` representable and meaningless. Run-level fields are the kind, `time_taken` and `error`; everything else is per-measurement
- [x] 3.5 Add the liveness submission route constant and the liveness batch content type mirroring the stress `SignedMessage` envelope. Lands in `nym-api-requests` and the validator-client route table rather than the orchestrator's request crate, because that is where the stress envelope lives; the endpoint is `POST /v3/nym-nodes/liveness-testing/batch-submit`. `ExercisedInterface` is DUPLICATED here rather than shared with the orchestrator's copy: the dependency runs orchestrator -> nym-api-requests, so sharing would be a cycle. The result carries no role field, since the interfaces exercised already determine the probed role and carrying both would let them disagree. `StressTestBatchSubmissionResponse` became an alias of a shared `BatchSubmissionResponse` rather than being copied, as both endpoints report the same three counts
- [x] 3.6 Unit-test that a gateway-liveness run serialises and round-trips both of its measurements, and that a single-measurement run round-trips unchanged. Both tests assert a byte-exact JSON fixed point rather than only field equality, which is what makes "unchanged" meaningful. Fixtures use distinct per-field values so a transposition fails, and nanosecond-remainder durations because every duration on this shape crosses the wire through `humantime_serde`; that pins the absence of silent precision loss, which would corrupt a measurement rather than fail it

## 8. Agent: liveness profile and wave concurrency

- [x] 8.1 Add the liveness probe profile alongside the stress profile in the tester config, carrying the per-target rate directly. The packet count is the primary knob and the send window derives from it (`count / rate`), inverting the stress profile's `rate x duration` shape, so `expected_packets()` cannot be shared between the two. The sending batch size is DERIVED from the packet count as a fixed number of dispatches across the window rather than inherited or configured: the interval is `batch / rate`, so the stress batch of 50 would collapse the profile's 50-packet probe into a single burst, and pinning a batch size instead of the dispatch count would break again the moment the provisional count or rate moves. Ack sizing needs no knob: both packet-building paths already use `PacketSize::AckPacket`, so liveness inherits it
- [x] 8.2 Bind ONE shared ingress listener per invocation, resolving each inbound connection to its target through one canonicalised source-keyed table and giving the responder a `NoiseNetworkView` scoped to just that connection's source. A wave-spanning view was specified here originally and turned out to be redundant: `upgrade_noise_responder` consults the view only via `supports_noise(source)` as a membership gate and `perform_responder_handshake` then reads only `config.local_key`, so the initiator's key plays no part on this side and a wave-wide view would duplicate the known-source set. A target's noise key is genuinely needed only by the INITIATOR (`get_noise_key`), which is its own egress connection. The listener must also stop handling one connection at a time, and its single `last_noise_handshake_duration` becomes per-source, since one field cannot attribute N targets. The ingress handshake stays MANDATORY per target rather than becoming optional: the harvest is only reached after that target's connectivity probe succeeded, and a returned packet means the node already connected back and handshook as responder, so the existing hard error is retained as a check on the new per-source plumbing. Small gain from the change: the source is known at accept time, before the handshake, so a FAILED ingress handshake becomes attributable to a target instead of an anonymous log line
- [x] 8.3 Make the known-source set the union of every target's announced addresses, canonicalised. Two targets in one wave announcing the same ip are deliberately NOT handled: the later one wins the ip-keyed slot, the other then presents an unexpected static key on its return connection, fails the responder handshake, receives nothing and scores zero while its twin scores normally. That is the intended penalty for a misconfigured pair, it is self-diagnosing from the results (a node permanently at zero beside a healthy twin), and both are still reached correctly on egress, which carries the port
- [x] 8.4 Attribute returned packets to a target by the source address of the connection they arrive on, and accumulate per-target results. Attribution is structural rather than per-packet: a connection resolves to its target once, before the handshake, and its handler then delivers to that target's `TargetInbox` alone. Accumulation is per TARGET rather than per connection because duplicates and counts are properties of a target's whole result set - a node may reply over more than one connection, and no single connection can tell whether an id has been seen already
- [x] 8.5 Execute a wave as one concurrent batch with a hard per-target deadline, so the wave's duration is bounded by the slowest single target. `NodeStressTester::run_stress_test` becomes `NodeProbe::run(profile)` now that it runs both kinds; the crate-local `TestRunResult` keeps its name
- [x] 8.6 Submit each target's result as soon as that target finishes rather than at the end of the wave, and never let one target's outcome abort the wave. A node-level failure (unreachable target, nothing returned) IS the measurement and MUST be submitted even when zeroed, because submission is what writes that pairing's `last_tested_at` and so defers the node a full staleness interval; hand-out advances only the address rotation pointer. A critical agent-side failure submits nothing and lets the lease expire instead, so the node keeps its turn rather than being scored zero for our bug, at the accepted cost that a persistently broken agent re-leases the same nodes every lease period, visible in the agent's logs only
- [x] 8.7 Unit-test attribution across a wave (several targets returning interleaved packets), and that one target timing out does not extend the others. ATTRIBUTION is covered at the connection handler's read level: `handle_stream` and `report_handshake` are generic over the stream, so tests instantiate them with a plain iterator of packets and assert per-target delivery, decrypting each with that target's OWN reusable header so a misdelivery fails to decrypt rather than merely landing in a bucket whose count happens to match. Five tests: concurrent connections delivering to their own targets, a connection from a target's other announced address, an unknown source dropped, a completed handshake ahead of its packets, a failed handshake reaching only its own target. The recorded trade is that they cover neither the socket accept nor the Noise upgrade.

      The TIMING half was examined and deliberately NOT unit-tested. `MixnetWave::run` binds a real listener and each probe TCP-connects and handshakes as initiator, so a target has to be a real endpoint; worse, a fake target that accepts and goes silent fails the Noise handshake and exits down the egress-failure path instead of reaching the deadline, so provoking a timeout needs a fake nym-node running `upgrade_noise_responder` with the key the probe expects and then going quiet. `tokio::time::pause` cannot be used alongside real sockets (auto-advance fires while a connect is pending), so the test would be real-time and timing-sensitive - the same flake this task's attribution half was seamed to avoid. What it would prove is `join_all` polling concurrently and `timeout` expiring, both library contracts; the agent's own logic is two lines. Covered instead by 12.4 end to end, plus two cheap guards over the pure functions that could regress silently: `each_kind_resolves_to_its_own_profile` (swapped arms would apply the wrong profile to both kinds) and `only_a_liveness_probe_carries_a_per_target_deadline` (losing the deadline would remove the bound entirely). Both were mutation-checked
