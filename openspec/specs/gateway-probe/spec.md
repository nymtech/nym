## Purpose

`nym-gateway-probe` is a Unix-only CLI diagnostic tool and reusable library that tests the health and connectivity capabilities of Nym mixnet gateway nodes. It connects to a gateway (resolved via the `nym-api` directory, or queried directly by IP for unannounced nodes) and exercises multiple transport paths — mixnet entry/exit routing, WireGuard-over-mixnet, Lewes Protocol registration, SOCKS5 network-requester connectivity, and WireGuard exit-policy TCP port reachability — then emits a structured JSON result.

## Requirements

### Requirement: The probe SHALL expose four run modes selected by subcommand

The CLI MUST provide four subcommands, each mapping to a distinct `Probe` run path:

- **`RunLocal`** — probe an *unannounced* gateway addressed by IP (`--entry-gateway-ip`, optional `--exit-gateway-ip`), bypassing directory lookup via a direct HTTP query. It MUST pass no mixnet client into the test sequence, so the mixnet ping and WireGuard-via-authenticator phases are skipped; LP registration MUST still be available because it is a direct TCP session and the node details are built by the same conversion used for directory nodes (LP data included whenever the node self-reports a validly signed `lewes_protocol` block). The SOCKS5 phase requires the tested gateway to appear in the fetched network topology, so for an unannounced node it records a connection failure rather than a useful result.
- **`Run`** — probe a *bonded* gateway resolved by identity through the `nym-api` directory.
- **`RunPorts`** — check WireGuard exit-policy TCP ports on a bonded gateway through the WG tunnel; `--check-all-ports` MUST use the full build-time `EXIT_POLICY_PORTS` list, overriding any `--check-ports`.
- **`RunAgent`** — the agent-driven run; it MUST force `test_mode = All`, use ephemeral storage, and import supplied ticket materials.

The global `--config-env-file` option MUST load the network environment; `--no-log` MUST disable tracing. Results MUST be pretty-printed as JSON to stdout; errors MUST print to stderr and exit non-zero. The binary MUST refuse to run on non-Unix targets.

#### Scenario: Bonded gateway core probe
- **GIVEN** a bonded gateway identity and a valid credential mode
- **WHEN** the `Run` subcommand executes with the default (`core`) test mode
- **THEN** the probe resolves the gateway via the directory, connects to the mixnet, and emits a `ProbeResult` JSON to stdout, exiting 0

#### Scenario: Unannounced gateway skips mixnet tests
- **GIVEN** `RunLocal` with `--entry-gateway-ip` for a node not in the directory
- **WHEN** the probe queries the node's HTTP API directly and runs `probe_run_locally`
- **THEN** no mixnet client is connected, `as_entry` is reported as `NotTested`, and only non-mixnet tests permitted by the test mode run

#### Scenario: Non-Unix target
- **WHEN** the binary is built/run on a non-Unix platform
- **THEN** it exits with an error rather than attempting to probe

### Requirement: Test-mode gating SHALL control which test phases run

A `TestMode` (default `Core`) MUST gate execution: mixnet tests run in `Core`/`All`; WireGuard tests run in `Core`/`WgMix`/`WgLp`/`All`; LP tests run in `WgLp`/`LpOnly`/`All`; SOCKS5 tests run in `Socks5Only`/`All`. The `mixnet` spelling MUST be accepted as an alias for `core`, and parsing MUST be case-insensitive across accepted spellings.

#### Scenario: LP-only mode skips mixnet and SOCKS5
- **GIVEN** `--test-mode lp-only`
- **WHEN** the probe runs
- **THEN** only LP tests are attempted and mixnet-routing and SOCKS5 phases are skipped

### Requirement: Test phases SHALL run in a fixed order with the mixnet client disconnected before LP/SOCKS5

`do_probe_test` MUST sequence phases as: mixnet ping → WireGuard (holding the mixnet client) → **disconnect the mixnet client** → LP registration → SOCKS5. Each phase MUST be gated by its `TestMode` predicate, and a failure in one phase MUST NOT prevent later phases (SOCKS5 errors in particular are logged and non-fatal); WG/LP results fall back to defaults on failure.

Neither of the two post-disconnect phases reuses the first mixnet client: LP registration is a direct TCP session to the node's LP control port, and the SOCKS5 phase builds its **own ephemeral SOCKS5 mixnet client** (fresh topology fetch, `request_gateway` pinned to the tested entry gateway, minimum gateway performance 0 and egress epoch role ignored so the node is not filtered out). A full `all` run therefore opens two independent client sessions to the same gateway, one before the disconnect and one after.

#### Scenario: SOCKS5 failure does not abort the run
- **GIVEN** `test_mode = All` and a SOCKS5 connectivity failure
- **WHEN** the SOCKS5 phase errors
- **THEN** the error is logged, `socks5` records the failure, and the overall `ProbeResult` is still emitted

#### Scenario: SOCKS5 connects independently of the earlier client
- **GIVEN** `test_mode = All`
- **WHEN** the SOCKS5 phase starts after the mixnet client has been disconnected
- **THEN** it builds and connects a new ephemeral SOCKS5 client to the same entry gateway rather than failing for want of a client

### Requirement: The probe SHALL acquire or import ecash credentials according to credential mode

For the `RunLocal`, `Run` and `RunPorts` subcommands, exactly one credential mode MUST be selected via a required, mutually-exclusive CLI arg group: `--use-mock-ecash` or `--mnemonic`. In mnemonic mode, if the credential store holds fewer than one ticketbook, the probe MUST acquire bandwidth for `V1MixnetEntry`, `V1WireguardEntry`, and `V1WireguardExit`. Mock-ecash mode MUST use a mock bandwidth controller and acquire nothing. `RunAgent` MUST NOT accept that arg group at all: it takes `--ticket-materials` (plus `--ticket-materials-revision`, default 1), decodes them into `AttachedTicketMaterials`, and imports them into an ephemeral client, so an agent run neither needs nor accepts a mnemonic or mock-ecash flag. Bandwidth acquisition MUST retry (up to 50 attempts, 1s backoff) and MUST treat "account sequence mismatch" as retryable.

#### Scenario: Fresh credential store triggers acquisition
- **GIVEN** mnemonic mode and an empty credential store
- **WHEN** the probe starts
- **THEN** it acquires ticketbooks for the mixnet-entry, wireguard-entry, and wireguard-exit ticket types before running tests

#### Scenario: Account sequence mismatch is retried
- **GIVEN** concurrent use of the same mnemonic causing an "account sequence mismatch" error
- **WHEN** bandwidth acquisition encounters it
- **THEN** the acquisition retries rather than failing the probe

### Requirement: The probe SHALL resolve target gateways via directory or direct IP query, verifying node signatures

For bonded gateways, `NymApiDirectory` MUST fetch all described nodes v2 from `nym-api`; entry lookups MUST require the node's declared entry role and exit lookups MUST require exit-gateway capability. When constructing a `TestedNodeDetails`, the probe MUST require at least one host IP and, when LP data is present, MUST verify the LP signature against the node identity (bailing on invalid). For unannounced nodes, `query_gateway_by_ip` MUST try multiple URL/port/scheme forms, require health status "up", verify the host-information signature, and require the gateway role to be enabled.

#### Scenario: Invalid LP signature is rejected
- **GIVEN** a directory node whose LP data signature does not verify against its identity
- **WHEN** the probe builds the tested node details
- **THEN** it bails with an error rather than probing with unverified LP data

#### Scenario: Direct IP query requires an enabled, healthy gateway
- **GIVEN** `RunLocal` against an IP whose node reports health "up" and a valid host-information signature
- **WHEN** the gateway role is not enabled
- **THEN** the direct query fails rather than returning a usable node

### Requirement: Mixnet ping tests SHALL measure entry connectivity and exit ICMP routing

When mixnet tests are enabled, the probe MUST first self-ping through the entry gateway; a self-ping failure MUST map to `fail_to_connect` (when the entry is under test) or `EntryFailure`. If an exit router address exists, the probe MUST send ICMPv4 and ICMPv6 echo requests to both the IPR tun-device addresses and external addresses (e.g. `8.8.8.8`, `2001:4860:4860::8888`), listen for beacon replies, and record which routes succeeded in the `Exit` result.

#### Scenario: Entry self-ping failure
- **GIVEN** the entry gateway is under test
- **WHEN** the self-ping through it fails
- **THEN** `as_entry` is recorded as `fail_to_connect`

#### Scenario: Exit routing recorded per address family
- **GIVEN** a reachable exit router
- **WHEN** ICMP echoes are sent to tun-device and external v4/v6 targets
- **THEN** the `Exit` result records `can_route_ip_v4`, `can_route_ip_external_v4`, `can_route_ip_v6`, and `can_route_ip_external_v6` from the observed replies

### Requirement: WireGuard tests SHALL register with the authenticator and run tunnel diagnostics via the Go netstack

WireGuard testing MUST perform the authenticator registration handshake (supporting authenticator versions V2–V6; V1/UNKNOWN MUST bail), extract the gateway WG public key, assigned private IPs, and WG port, and build a `WgTunnelConfig`. It MUST then run the blocking Go netstack tunnel tests on `spawn_blocking`, recording handshake, metadata query, DNS resolution, ping performance ratios, download metrics, and (in port-check mode) port-check results, for IPv4 and IPv6. `can_register` MUST be determined by the handshake, not the netstack call. In `port_check_only` mode the netstack pass MUST return after IPv4 (skipping IPv6).

#### Scenario: Successful registration sets can_register
- **GIVEN** a gateway with a functional authenticator
- **WHEN** the registration handshake completes
- **THEN** `WgProbeResults.can_register` is true and tunnel tests run over the established config

#### Scenario: Unsupported authenticator version
- **WHEN** the authenticator reports version V1 or UNKNOWN
- **THEN** the WireGuard test bails rather than attempting registration

### Requirement: LP (Lewes Protocol) registration testing SHALL probe handshake then dVPN registration

When LP tests are enabled and the node has LP data, the probe MUST build an `LpRegistrationClient`, perform the LP handshake under a 15s timeout (setting `can_connect`/`can_handshake` on success; recording an error and returning early on failure), then attempt `register_dvpn` with `V1WireguardEntry` under a 15s timeout (setting `can_register` on success). When LP tests are enabled but the node has no LP data, the probe MUST emit `LpProbeResults` with all flags false and `error = "no LP data"`.

#### Scenario: LP requested but no LP data
- **GIVEN** `test_mode = lp-only` and a node whose description lacks LP data
- **WHEN** the LP phase runs
- **THEN** `lp` is `{ can_connect: false, can_handshake: false, can_register: false, error: "no LP data" }`

#### Scenario: LP handshake timeout
- **GIVEN** an LP-capable node that does not complete the handshake within 15s
- **WHEN** the handshake times out
- **THEN** the LP result records a handshake-timeout error and dVPN registration is not attempted

### Requirement: SOCKS5 testing SHALL verify HTTPS connectivity through a SOCKS5-over-mixnet proxy

SOCKS5 testing MUST build an ephemeral SOCKS5 mixnet client pinned to the entry gateway (with minimum gateway performance 0 and egress epoch role ignored, so the tested gateway is not filtered out of topology), fetch its own topology, and connect. On connect failure it MUST return `error_before_connecting`. On success it MUST run up to `test_count` HTTPS/JSON-RPC (`eth_chainId`) requests with endpoint fallbacks, early-exiting once the unsuccessful count exceeds `failure_count_cutoff`, and aggregate results (including average latency over successes) into `HttpsConnectivityResult`.

#### Scenario: SOCKS5 connect failure
- **GIVEN** the ephemeral SOCKS5 client cannot connect through the tested gateway
- **WHEN** the SOCKS5 phase runs
- **THEN** the result records `error_before_connecting` and no HTTPS tests are attempted

#### Scenario: HTTPS connectivity aggregation
- **GIVEN** a working SOCKS5 proxy and configured JSON-RPC endpoints
- **WHEN** the probe issues its HTTPS test iterations
- **THEN** it records success, an HTTP status code, and average latency, falling back across endpoints on failure

### Requirement: The ports-check flow SHALL select a reachable target, register with retries, and report per-port reachability

The ports-check run MUST reject exit nodes that lack an authenticator address or IP ("not a functional exit") and MUST reject a request for zero ports. When multiple comma-separated targets are given it MUST select the first reachable on TCP 80 or 443 (2s timeout), else fall back to the first. It MUST warm up routes, then attempt authenticator registration up to 3 times (5s between attempts, fetching a fresh `V1WireguardExit` ticket each attempt), and run an IPv4-only netstack port scan. The output MUST be a `PortCheckResult` with a deterministic `BTreeMap` of port→open, `can_register`, the selected target, and an optional error.

#### Scenario: Non-functional exit rejected
- **GIVEN** a target gateway with no authenticator address
- **WHEN** the ports-check setup runs
- **THEN** it bails with a "not a functional exit" error and produces no scan

#### Scenario: Registration retried up to three times
- **GIVEN** transient authenticator registration failures
- **WHEN** the ports-check attempts registration
- **THEN** it retries up to 3 times with a fresh wireguard-exit ticket per attempt before giving up

### Requirement: The probe SHALL emit structured, serializable result types

The probe MUST output one of two shapes: a `ProbeResult { node, used_entry, outcome }` where `outcome: ProbeOutcome { as_entry, as_exit, socks5, wg, lp }`, or a `PortCheckResult { gateway, can_register, port_check_target, ports (BTreeMap), error? }`. Result types MUST derive OpenAPI schemas when the `utoipa` feature is enabled so downstream services can consume them. Port maps MUST use `BTreeMap` for deterministic ordering (so signed submissions are stable).

#### Scenario: Standard probe output shape
- **WHEN** a `Run`/`RunAgent`/`RunLocal` probe completes
- **THEN** stdout contains a JSON `ProbeResult` with `node`, `used_entry`, and an `outcome` object containing the per-transport sub-results

#### Scenario: Deterministic port map ordering
- **WHEN** a ports check completes
- **THEN** the `ports` map is a `BTreeMap`, giving stable ordering suitable for deterministic (bincode) signing downstream

## Technical Notes

- **Implementation**: `nym-gateway-probe/src/lib.rs` (`Probe`, run variants, `do_probe_test`), `common/probe_tests.rs`, `common/wireguard.rs` + `common/netstack.rs` (Go FFI), `common/nodes.rs` (discovery), `common/socks5_test/`, `config/` (args, test mode, credentials), `common/types.rs` (result shapes).
- **Protocols**: Nym mixnet (Sphinx via `nym-sdk`), WireGuard (+ Amnezia-WG) tunnelled over mixnet with authenticator registration, Lewes Protocol over raw TCP, SOCKS5 with Ethereum `eth_chainId` JSON-RPC probes, ICMP echo via `pnet_packet`/`nym-connection-monitor`.
- **Go FFI**: WireGuard netstack tunnel tests are implemented in Go (`netstack_ping`) compiled to a static C archive at build time (macOS/linux, amd64/arm64); Rust calls `wgPing`/`wgFreePtr` over JSON and must run them on `spawn_blocking`.
- **Build-time codegen**: `build.rs` parses `PORT_MAPPINGS` from `scripts/nym-node-setup/network-tunnel-manager.sh` into a sorted, de-duplicated `EXIT_POLICY_PORTS`.
- **Dependencies**: [[node-status-agent]] embeds this crate as a library; result types are consumed by [[node-status-api-testruns]].
