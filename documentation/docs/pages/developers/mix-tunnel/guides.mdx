# Reference

## Configuration

`setupMixTunnel(opts)` accepts the full smolmix-wasm `SetupOpts` surface plus one TS-layer addition (`debug`). Pass any subset; every field has a default (listed in [`SetupMixTunnelOpts`](/developers/mix-tunnel/api/interfaces/SetupMixTunnelOpts)).

```ts
await setupMixTunnel({
  // Pin a specific IPR (otherwise auto-discovered from the topology).
  preferredIpr: 'D1rrUqJY9pesL3pTaMaxLnpZGGYQ4ZpZwpQXCqaeBXTW.6PpFkRvF...',

  // Cover traffic and Poisson timing are ON by default. Setting these disables
  // them for lower latency and bandwidth, at the cost of traffic-analysis
  // resistance (it drops timing-correlation resistance at the entry and exit).
  disableCoverTraffic: true,
  disablePoissonTraffic: true,

  // Verbose console tracing from smolmix-wasm. Useful while integrating.
  debug: true,
});
```

The complete option surface (IPR pinning, SURB budgets, DoH resolver list, TCP/connect timeouts, gateway selection) is documented in the [`SetupMixTunnelOpts` type reference](/developers/mix-tunnel/api/interfaces/SetupMixTunnelOpts).

<Callout type="info">
Call `setupMixTunnel` once. The WASM tunnel is one-shot per page: the first call brings it up, and a second call rejects with `tunnel already initialised`. Because the feature packages share that one tunnel, calling it from `mix-fetch` is enough for `mix-dns` and `mix-websocket` too. If more than one call site might invoke it, guard with `getTunnelState()` and skip setup when the state is already `ready`.
</Callout>

## How the tunnel connects

`setupMixTunnel` does two things that shape how long it takes and what you can tune: it selects an exit IPR, and it sets up DNS.

### Exit selection and retry

With `preferredIpr` set, setup connects to that one exit and waits out `connectTimeoutMs` (default 60000) if it is slow. Nothing rotates, because you named the exit.

Without it, setup ranks the eligible exits by performance and tries them in order. Each exit gets a short budget (`iprAttemptTimeoutMs`, default 6000); if the handshake does not complete in that budget, setup moves to the next exit, up to `iprMaxAttempts` (default 5). A dead or overloaded exit costs a few seconds rather than the full connect timeout, and setup succeeds as long as one eligible exit is healthy. Both budgets apply only on this auto-discovery path:

```ts
await setupMixTunnel({
  iprAttemptTimeoutMs: 6000, // per-exit handshake budget before rotating
  iprMaxAttempts: 5,         // exits to try before giving up
});
```

One handshake detail helps when reading `debug` logs. An exit's directory version can advertise a newer protocol than the binary it runs, so the client probes the newer version and, on no reply, retries the older one against the same exit. A connect that logs `v10 connect timed out; retrying v9` and then succeeds is that fallback doing its job; the connection is fine. It adds about one budget to that connect.

### DNS

Name resolution runs over DNS-over-HTTPS through the same tunnel. See [mix-dns](/developers/mix-dns/guides) for the resolver list (`dohEndpoints`) and the security model. The first lookup opens a TLS connection to the resolver and pays that handshake; later lookups reuse the warm connection and return in well under a second. A rate-limited resolver answers HTTP 429, which surfaces as an error and moves setup to the next endpoint instead of stalling until a timeout.

## Tunnel state

`getTunnelState()` returns a tagged state for surfacing connection status in the UI. The five states are:

| State | Meaning |
|---|---|
| `connecting` | Default before `setupMixTunnel()` completes. |
| `ready` | Tunnel is up. Feature packages can issue requests. |
| `shutting_down` | `disconnectMixTunnel()` in progress. |
| `shutdown` | Cleanly torn down. The WASM is no longer usable. |
| `failed` | Setup or runtime error. Carries a `reason`; the other four states have no extra fields. |

`reason` is a tagged object, not a string. It is either
`{ kind: 'task_exited', task: 'bridge' | 'reactor' }` or `{ kind: 'task_panicked' }`, so
switch on `reason.kind` rather than printing it directly.

`TunnelState` is a discriminated union, so narrow on `state` before reading `reason`:

```ts
const tunnel = await getTunnelState();
if (tunnel.state === 'failed') {
  const { reason } = tunnel;
  console.error(
    reason.kind === 'task_exited'
      ? `Tunnel failed: the ${reason.task} task exited`
      : 'Tunnel failed: a task panicked',
  );
}
```

Each variant is exported under its own name (`TunnelConnecting`, `TunnelReady`,
`TunnelShuttingDown`, `TunnelShutdown`, `TunnelFailed`) for writing type guards.

`await setupMixTunnel()` resolves only once the tunnel is `ready`, so most apps never need to read the state. Poll `getTunnelState()` only to drive a separate status indicator. The transitions are coarse (no progress percentage during `connecting`); the underlying connection events are visible via `debug: true` in the console.
