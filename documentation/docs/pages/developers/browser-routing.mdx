# Routing a browser or WebView app

This page covers the web-runtime reasons a mixnet routing policy fails to bind,
and the traffic that no policy can reach. A WebView host runs the same web
platform as a browser tab, so it applies to both. Capacitor, Cordova, WKWebView
and Android WebView are in scope.

Requests leave a web app from several places: your own `fetch` helper, libraries
that call the global `fetch`, cross-origin iframes, vendor SDKs and Web Workers.
You control the first. A routing policy written in application code
covers less than it appears to, and a policy that fails to bind raises no error.
The request succeeds, returns the data you expected, and travels over the
clearnet.

[Planning an integration](/developers/integrating) decides *what* to route. This
page assumes you have that list.

## Why a routing policy does not bind

A single module that wraps `fetch`, imported in twenty places, looks like a
choke point. Two things stop it being one, and neither announces itself.

The wrapper only binds code that imports it. JavaScript resolves a bare
identifier by scope, so a call site that forgot the import still compiles, still
runs, and still returns real data. The only visible sign is in the network
panel: an `HTTP/2` connection and a round trip of tens of milliseconds, which no
mixnet request produces. Search for the bare identifier, not only for the import.

Libraries also bring their own transport. Ethers calls the global `fetch` from
its own web layer, so routing it means subclassing the provider and overriding
`send()`. The same holds for `axios`, `got`, or any generated API client. Audit
the transports in your dependency tree, not the call sites in your own code.

## What cannot be routed from a web runtime

Some traffic is unreachable from your JavaScript, however carefully you work.
Being explicit about this matters more than the part that works, because it is
what your users are still exposed to.

| Source | Why it is out of reach |
|---|---|
| Cross-origin iframes | A separate browsing context with its own networking. Embedded swap widgets, on-ramp providers and dApp frames route nothing through your code. |
| Vendor SDKs in their own contexts | Payment and identity providers, analytics loaders, and connect libraries that open their own windows or frames. |
| Third-party WebSocket relays | [`mix-websocket`](/developers/mix-websocket) carries `ws` and `wss`, but its constructor is asynchronous and it exposes no `bufferedAmount`. To drop it in for a synchronous `WebSocket` inside someone else's library, you write an adapter for that library. |
| Hardware wallets | Some paths are local and touch no network at all (WebHID, WebUSB). Others reach out from a vendor-hosted page that you do not control. |
| Browser-initiated requests | `navigator.sendBeacon`, `EventSource`, `<img>` and `<script>` sources, and prefetch hints. |

A destination in that table may learn something you want to hide. Transport is
then the wrong layer to fix it at. Drop the integration, move it behind your own
backend, or record it as accepted in your threat model.

## Detecting requests that bypass the policy

Wrap `window.fetch` and `XMLHttpRequest.prototype.open` at startup, and treat
any direct request to a routed host as a leak. The mixnet path never touches
those globals for those hosts. A hit is a bug in your own code, with no false
positives to triage.

```js
const ROUTED_HOSTS = new Set(['api.example.com'])
const FAIL_CLOSED = false

const isRouted = (url) => ROUTED_HOSTS.has(new URL(url, location.href).hostname)

function onLeak(url) {
  console.error('nym leak guard: direct request to routed host', url)
  if (FAIL_CLOSED) throw new Error(`blocked direct request to ${url}`)
}

export function installLeakGuard() {
  const nativeFetch = window.fetch
  window.fetch = function (input, init) {
    const url = input instanceof Request ? input.url : String(input)
    if (isRouted(url)) onLeak(url)
    return nativeFetch.call(this, input, init)
  }

  const nativeOpen = XMLHttpRequest.prototype.open
  XMLHttpRequest.prototype.open = function (method, url, ...rest) {
    if (isRouted(String(url))) onLeak(String(url))
    return nativeOpen.call(this, method, url, ...rest)
  }
}
```

`FAIL_CLOSED` is the same decision as
[fail-open or fail-closed](/developers/integrating#decide-fail-open-or-fail-closed-explicitly),
made one request at a time. Run it on in development, where a network error in
code that did not expect one is cheaper than a leak.

The guard does not see `navigator.sendBeacon`, `EventSource`, `WebSocket`,
`<img>` and `<script>` sources, or anything inside a cross-origin iframe. Those
need enforcement, below.

## Proving the mixnet did the work

A leak guard proves that your code ran. It says nothing about whether the tunnel
carried anything. To test that, ask one echo service over both paths and compare
what it saw:

```js
const sourceIp = async (get) => (await (await get('https://echo.example/ip')).json()).ip

const [clearnet, mixnet] = await Promise.all([
  sourceIp((u) => fetch(u)),
  sourceIp((u) => mixFetch(u)),
])

console.log({ clearnet, mixnet, differ: clearnet !== mixnet })
// { clearnet: "203.0.113.9", mixnet: "51.x.x.x", differ: true }
```

Hang it somewhere you can reach from the console. No other check separates a
request that went through the tunnel from transport code that ran without
throwing.

## Enforcing with Content Security Policy

`connect-src` is the only browser-enforced answer, and the mechanism behind it
is not obvious. Mixnet payload traffic never reaches CSP as a connection to your
destination. It is a WebSocket to a Nym gateway, and the TLS session terminates
inside the WASM. Leave the routed host out of `connect-src`. Every direct path
to it is then blocked, and the mixnet path keeps working.

That combination is what proves the routing. A request succeeds while the
browser refuses every direct connection to its destination, so it can only have
come through the tunnel.

```text
connect-src 'self' wss: https://validator.nymtech.net
            https://cdn.example.com https://prices.example.com;
worker-src 'self' blob:;
```

`worker-src 'self' blob:` is required. `mix-tunnel` base64-decodes its Web
Worker and starts it from an object URL. With no `worker-src`, CSP falls back to
`script-src` and the browser blocks it. Raise the cost of that in review,
because `blob:` permits worker code that did not come from your origin.

`wss:` has to stay broad. Gateway hostnames come from the network topology at
runtime, so you cannot enumerate them in advance.

Turning enforcement on early is also the cheapest way to find out what your app
talks to. Run with a deliberately incomplete `connect-src` and read the
violations as a map. Expect it to name destinations that appear in no config
file.

### The nym-api bootstrap is policed even though payload traffic is not

Payload traffic is invisible to `connect-src`. The client's own bootstrap is
not. Before any mixnet traffic exists, the client fetches the network topology
from the nym-api over ordinary HTTPS, and uses it to pick a gateway. That
request answers to the policy like any other.

Leave it out, and the tunnel dies at startup with a gateway selection error. The
error never mentions CSP. On mainnet the host is `https://validator.nymtech.net`.

Enforcement has to allow the control plane and still deny the data plane's
destination. They are different hosts, which is the only reason this works.

<Callout type="warning">
CSP is an allowlist, so you cannot deny a single host. Leaving your routed
destination out means enumerating every other destination the app uses, and
keeping that list current. Add an endpoint anywhere in the app and forget the
list. The browser then blocks it in production, after it worked in every local
test that carried no policy.

Roll out with `Content-Security-Policy-Report-Only` as a *header* first, which a
`<meta>` tag cannot express, and collect violations from real sessions. Check
for a policy already set server-side as well. Multiple policies intersect and
the narrower one wins. A header that carries `default-src` or `script-src`
without `blob:` defeats anything you change in a `<meta>` tag.
</Callout>

## Keeping the WASM out of your initial payload

Pull the Nym packages in with a dynamic `import()` behind a named chunk. They
are then fetched when the mixnet is first used, and never land in the initial
bundle:

```js
let tunnelPromise

export function ensureTunnel() {
  tunnelPromise ??= import(/* webpackChunkName: "nym-mixnet" */ '@nymproject/mix-tunnel')
    .then((m) => m.setupMixTunnel({ /* opts */ }))
  return tunnelPromise
}
```

Memoising the promise does more than tidy the code. The tunnel is one-shot per
page, and a second `setupMixTunnel` call rejects, so
[the guidance](/developers/mix-tunnel/guides#tunnel-state) is to guard on
`getTunnelState()`. That guard races. Two call sites can check while the state
is `connecting`, and both then call setup. One of them takes the rejection. A
memoised promise has no such window, and it hands concurrent callers one
bring-up to await instead of a state to poll.

Add one thing before you ship it. `??=` caches a rejection as durably as it
caches a success. A chunk that fails to load once leaves every later caller
awaiting that rejection for the life of the page. So does a `setupMixTunnel`
that rejects because something else brought the tunnel up first. Clear
`tunnelPromise` in a `catch`, so that the next call retries.

Expect several megabytes gzipped for the chunk. The worker arrives as one long
base64 line, which makes minification the memory-hungry step of your build. A
build that dies with a bare `Killed` was stopped by the out-of-memory killer,
not by a code error.
